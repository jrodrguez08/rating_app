# Coding agent instructions

`AGENTS.md` is the canonical agent instruction file. Do not add tool-specific copies such as `CLAUDE.md`, `GEMINI.md`, or `CODEX.md` unless a concrete integration cannot reference this file.

Before product-code changes, read this file completely along with `PRODUCT.md`, `ARCHITECTURE.md`, and `DESIGN_SYSTEM.md`. Those four files are the canonical product, architecture, design, and implementation guidance.

- Preserve product invariants: participant-only ballots, one voter/match ballot, hidden in-window aggregates, and club-neutral domain modeling.
- Keep Herediano-specific names and colors in configuration/presentation, not collection names or generic entities.
- Prefer Server Components; add `"use client"` only for concrete browser behavior.
- Keep code simple, typed, and direct. Keep strict TypeScript enabled, use explicit domain types, infer clear local types, prefer `unknown` to unsafe `any`, and narrow values before use.
- Order imports as framework/external, internal `@/` imports, then relative imports. Use type-only imports where appropriate. Keep imports conventional, unique, and free of unused symbols; do not add cosmetic barrel files.
- Prettier is the formatting authority. Run `npm run format` for intentional formatting and do not add stylistic ESLint rules that compete with it. Preserve UTF-8, LF endings, two-space indentation, and final newlines.
- Keep user-facing source text as valid UTF-8 and run `npm run check:encoding` to catch known mojibake markers; fix corrupted literals at their source rather than adding runtime decoding or replacement logic.
- Update meaningful tests when behavior changes. Test outcomes and accessibility semantics, not implementation trivia.
- Treat documentation review as part of every bug fix, hotfix, feature, and refactor that changes or clarifies durable product behavior, lifecycle rules, architecture, operational behavior, or invariants. Update the relevant canonical source-of-truth document in the same change when needed, and explicitly report whether documentation changed or why no update was required. Do not defer durable documentation cleanup to a later task.
- Update source-of-truth documentation when product or architecture truths change.
- Never commit secrets or local environment files. Keep `.env.example` placeholder-only and keep local work on emulators or an explicit development Firebase project.
- Treat `teams/{teamId}` as public-readable and client-write-denied. Seed only through the explicit emulator bootstrap; never seed from rendering or application startup and never weaken rules for convenience.
- Keep football providers behind `FootballDataProvider`. Never import provider DTOs into UI or domain models, expose `API_FOOTBALL_KEY` to the browser, or run privileged sync persistence against a non-local or non-`demo-*` Firebase target.
- Preserve sync idempotency and bounded provider reads. Match imports must handle the tracked Team as home or away and must not imply that lineups, participants, coaches, or voting data were synchronized.
- Rating eligibility requires both tracked-Team ownership and confirmed match participation. Opponent players/coaches and unused or unconfirmed substitutes are never rateable. Keep participant DTOs behind `FootballDataProvider`, preserve participant/coach sync idempotency, and allow late provider data to correct participation before lifecycle code consumes it. Fixture lineup evidence remains authoritative for the head-coach slot. If the lineup supplies a valid coach name but no usable numeric provider ID, only an unambiguous exact normalized-name match from the tracked Team's `/coachs?team=...` response may recover the stable ID. If the provider publishes the coach object with neither usable ID nor name, recovery requires exactly one `/coachs?team=...` candidate whose tracked-Team career interval covers the persisted fixture kickoff date. Never infer from latest/current coach state alone, invent IDs, or fuzzy-match coach identity.
- Treat fixture-specific operator-verified coach recovery as an exceptional server-only operation. Preserve its Team/fixture binding, evidence, operator audit, and provenance; never invent a provider identity, inherit an assignment across matches, or let automatic sync overwrite a verified assignment. Participant evidence and the accepted coach assignment must be persisted atomically, and the normal lifecycle alone decides readiness.
- Treat fixture-specific operator-verified lineup preparation as a server-only recovery path. Bind every snapshot to the exact Match, provider fixture, tracked Team, canonical Players, evidence, reason, operator, and trusted timestamp. Preserve exactly 11 confirmed starters; only confirmed entering substitutes are rateable, while unused and unconfirmed substitutes remain ineligible. After provider `lineup-unavailable`, a complete verified lineup plus a fixture-bound verified head coach may satisfy final participant context without provider IDs; every other provider failure and a missing verified coach remain retryable. Never invent provider IDs, infer identity from names or shirts, let provider sync silently replace verified participation, mutate participants after voting or protected history exists, or set voting state from the admin operation.
- Keep the visual lineup editor as local draft state over the verified lineup preparation service. Preload a valid fixture-bound verified snapshot before persisted provider participants, search the configured Team's canonical Players only through bounded owner-authorized server reads, and keep drag-and-drop optional through equivalent click and keyboard controls. Bench membership never confirms participation, and visual moves never write Firestore before the explicit audited apply.
- Keep lifecycle polling match-aware and on zero-additional-cost infrastructure unless explicitly approved. Provider `FT` alone never opens a window: tracked-Team participant and head-coach readiness must succeed first. Preserve the first server-controlled voting timestamps across retries, keep privileged lifecycle writes server-only, and never expose cron, provider, or Admin secrets.
- Keep owner lifecycle requests durable after authorization. Persist `requested`, `running`, `skipped_busy`, `completed`, `failed`, or `voting_open` separately from Match `ratingState`; bind bounded retries and status checks to the original consumed challenge and audit without duplicating either. Reconcile a busy request only against its observed lifecycle attempt and Match. Renew and verify the shared execution lease around bounded provider reads, and fence stale attempts from releasing a newer lease.
- Use Firebase UID as the canonical `voterId`; reuse the persistent anonymous identity and do not expose it or add visible login/reset friction. Authentication grants no general Firestore access. Keep ballot documents client-denied: the trusted ballot endpoint must verify the ID token, derive the deterministic voter path, reload authoritative eligibility/window data in its create-only transaction, and accept only a complete exact 1–10 integer ballot.
- Add every user-visible product string through the i18n layer with both Spanish and English translations; hardcode only proper nouns or documented technical exceptions. Preserve Spanish as the default/fallback, use shared locale-aware date/number formatters, and never create translated copies of provider/domain entities.
- Never expose aggregate voting information before trusted close time. Ballots remain private; trusted server code must reuse canonical ballot/eligibility validation and idempotently create the immutable final result. The coach is never part of player MVP ranking.
- Treat voting-window reopen and early close as exceptional production operations. Preserve original window timestamps and ballots, archive an existing result before reopening, use the shared transactional aggregation path for close, require the separate configured operator secret plus production Admin credentials, and keep these controls out of supporter routes and UI.
- Keep voting-window operator notification server-only, idempotent per original/reopened window, and non-blocking. Delivery or configuration failures must preserve the active window and remain safely retryable without exposing the operator address or provider credentials.
- Follow the 16-bit sports-game visual language in `DESIGN_SYSTEM.md` while preserving modern usability; do not introduce generic SaaS/dashboard styling. Apply club colors only through presentation theme tokens.
- Use the central typography roles: DotGothic16 only for short, high-impact game/score UI and the readable sans for body copy and long names. Do not add arbitrary font-family declarations.
- Run `npm run test:firebase` for Firestore persistence or rules changes. It requires Java and the externally installed Firebase CLI; CI runs it separately from the standard gate.
- Do not edit or commit generated output such as `.next`, coverage, emulator data, `next-env.d.ts`, or TypeScript build-info files.
- Use `npm run verify` as the complete local quality gate: formatting, lint, strict typecheck, all tests, and production build. Also run `git diff --check` before handoff. Wait for every process to exit and never report a command as passing while it is still running.
- Keep Git changes scoped and preserve unrelated user work. CI must use `npm ci` and invoke the same canonical verification command without production credentials.
- Production must never use demo projects or emulator hosts. Keep local seed/sync commands emulator-only; production mutations require an explicit trusted path, exact project confirmation, and the complete verification gate.
- Keep `/admin` owner-only and server-authorized: use the isolated named browser Auth instance, require the exact configured Firebase UID and verified password provider on every request, and preserve revocation-aware short sessions, origin/CSRF checks, no-store responses, and deny-all client Firestore access. Sensitive web mutations also require a throttled, short-lived, one-use passphrase challenge bound to the exact action; never log or persist its plaintext. Commit challenge consumption, the mutation, and its deterministic success audit in one transaction so a successful web mutation cannot exist unaudited. Exact retries may only read and return that durable receipt, even after later Match lifecycle changes; they never authorize or repeat the mutation. Keep focused services such as `AdminVerifiedCoachService` and `AdminVerifiedLineupService` as the mutation boundaries.
