# Issue #155: Firestore read investigation

## Conclusion and evidence limits

Firestore quota exhaustion is confirmed; attribution of the approximately 55,000 daily reads is **inconclusive**. The issue records a rounded Firebase Usage counter, 329 writes and zero deletes. Read/write ratios cannot identify a caller. No production database traversal, import, backfill, configuration change or mutation was performed for this investigation.

Read-only Vercel evidence retrieved during the incident:

- Production deployment `dpl_2kwMtrJ139hesNGtF6CSJYSvH1zA`, commit `6f8b8ef`, was READY; created November 5 at 12:36:51 Costa Rica time. Photo-enrichment commit `46351e4` had READY production deployments created at 11:20:03 and 11:39:24. These are deployment creation times, not exact traffic cutovers.
- Retained logs show `8 RESOURCE_EXHAUSTED: Quota exceeded.` on the affected admin Match route at 19:33:41, 19:35:37 and 19:35:51 Costa Rica time (November 6 at 01:33–01:35 UTC).
- A recent approximately 50-minute log grouping returned 36 lifecycle log entries, 11 Herediano Home entries, two Saprissa Home entries, three admin Match entries and one draft entry. **Log entries are not request counts**: one lifecycle execution emits multiple events. The retained window does not establish daily traffic or import volume.
- The full incident-day runtime-log request was rejected because it exceeds Hobby retention. No connected Firebase Usage/Cloud Monitoring time series or per-query billing attribution was available. Current production Match counts were deliberately not scanned during quota exhaustion.
- Reviewed [#145](https://github.com/jrodrguez08/rating_app/issues/145), [#148](https://github.com/jrodrguez08/rating_app/issues/148), [#152](https://github.com/jrodrguez08/rating_app/pull/152), [#155](https://github.com/jrodrguez08/rating_app/issues/155) and their merged implementation. #148's earlier observation of 31 Saprissa and 33 Herediano Players is historical context, not a current database census.

Ranked explanations requiring production correlation:

1. **Repeated public reads, especially Home and complete catalog/history pages.** Confirmed amplification: Home read every Match for each request, without cross-request caching. Public player profiles build the complete club catalog/history. These are plausible recurring contributors; daily request counts are unavailable.
2. **Recurring Team-scoped lifecycle scans plus page traffic.** Lifecycle reads all that Team's Matches once, or twice when discovery is due; standings also reads the Team's Match list daily. The 30-minute cadence is bounded, but document cost grows with history. A shared fixture has separate club Matches and independent executions. No evidence establishes that these jobs alone exhausted quota.
3. **Owner catalog, search, reconciliation and preparation activity.** Catalog preview redundantly reread aliases, but no catalog HTTP path performs a global Player/Coach/history scan. Normal preview costs hundreds, not tens of thousands, of reads in the reproduced datasets. Repetition and full identity suggestion/history reviews can accumulate cost. There is no retained incident-day operation timeline to establish causation. Import/photo enrichment alone is not a confirmed root cause.
4. **Explicit offline audits/backfills or external console activity.** These can traverse history; no available evidence shows they ran that day. Browser source contains no Firestore snapshot listener or automatic polling loop. Operator actions and locale refreshes can intentionally cause new server requests.

## Reproduction and measurements

`tests/firebase/read-counts.ts` observes real Admin SDK Query/getAll/transaction calls against emulators. It counts unique paths per batch, missing documents, and the minimum one read for an empty query; repeated transaction callbacks remain visible. Emulator billing is not measured. Index-entry charges, Auth/session checks, failed RPC billing and other requests are excluded. Provider requests are a separate counter.

Before changing product code, the focused baseline suite completed with exit 0: two files, 17 tests. The same synthetic workflows now have regression budgets:

For direct one-provider-ID-per-identity catalogs where squad IDs overlap fixture IDs, preview costs `7 + 4P + 3C` before and `7 + 3P + 2C` after. More generally, let A be distinct initially fetched aliases, D the signed-state references, and H the overlap between them: `4 + A + D` becomes `4 + A + D - H`. Prelude cost four includes the cooldown read; contention can add attempts. Apply remains `1 + D` per attempt. Preview UI/log counts describe its successful repository reads without Auth checks; reconstructed apply receipts retain the earlier conservative preview estimate because squad-only observations are not retained in the action.

Home now scales with rating-ready windows W, not historical M: W (or one minimum empty read), plus at most five single-document/minimum queries, plus an empty terminal page when W is an exact multiple of 50. All windows must remain discoverable regardless of kickoff age because operator reopen is supported. More than 100 read units marks the Home metric expensive; investigate accumulated windows rather than truncating them.

These improvements cannot prove how the 55,000 incident reads were distributed. For example, 1,000 uncached Home requests over 50 Matches would alone consume 50,000 document reads before this fix; this is an illustrative estimate, not observed traffic. Remaining complete archive, Player-history and lifecycle reads need production volume measurements before a larger projection or cache is justified.

## Release and safeguards

- Deploy the two new `matches(trackedTeamId,status,kickoffAt DESC)` and `matches(trackedTeamId,votingOpeningMode,kickoffAt DESC)` collection indexes and wait for READY **before** the application release. Existing indexes cover rating-ready, live and upcoming queries. Emulator tests do not prove production composite-index readiness. No schema/data migration, backfill, credential, paid service or Firestore rule change is needed.
- No response cache was added. Home evaluates effective windows on every request; ballot, lifecycle and result publication boundaries retain fresh authoritative checks. No change to eligibility, aliases, protected evidence, windows, results, notifications or owner authorization.
- `firestore.home_read` records Team, query attempts, successful document-read estimate, completed/failed and expensive flags. `firestore.match_list` records Team/list cost for remaining complete-list consumers. The existing `admin.catalog_import_preview` event adds the measured preview read estimate. These logs add no Firestore writes and no identity, voter, ballot, token, cookie, evidence or provider payload. Logging failure cannot alter behavior.
- Failed Home reads propagate to the existing honest unavailable state, with no new retry loop or partial-data fallback. Failed-RPC read costs are unknown and are not reported as zero billed usage by these estimates.
- Monitor daily usage and capture logs during retention using the runbook. No alerting resource or paid plan was configured. Do not merge/deploy automatically; do not run production imports/backfills to validate this change.

Product and design documentation were reviewed: supporter behavior, visual language and localized copy do not change. Architecture and production runbook describe the changed access costs and release prerequisites.

Local browser verification also exposed an existing harness/environment interaction: Next loaded the developer's `.env.local` and dotenv expansion corrupted the injected synthetic passphrase verifier. The captured lineup passed the domain service directly; a temporary safe stage/category diagnostic identified the failing web receipt as missing passphrase configuration. The E2E server now explicitly uses `NODE_ENV=test` to exclude `.env.local`. The diagnostic was removed; no local secret or production setting was changed.
