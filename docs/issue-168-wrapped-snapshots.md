# Wrapped snapshot lifecycle

Phase 2C runs only against loopback Firebase emulators in a `demo-*` project. Herediano and Saprissa have independent state for each exact edition. Hosted execution and presentation are disabled. The reviewed ledger and calculator follow [coverage](issue-164-wrapped-coverage.md) and [statistics](issue-166-wrapped-statistics.md). The pilot thresholds remain provisional.

## Owner procedure

Use the local app with the existing verified owner account, admin session, allowed Origin, CSRF cookie and passphrase configuration. Send JSON requests to `POST /api/admin/wrapped?club=<slug>` with the admin cookies and `x-admin-csrf`. The route derives the Team from the registered club.

1. Send `step: preview`, `operation: approve`, the exact `tournamentKey`, and the reviewed Phase 2A `ledger`. Check the sanitized projection, sample gate, coverage and awards against the reviewed scope. This dry run performs zero application writes.
2. Send `step: authorize` with the same operation and key, `digest` and `epoch` from the preview action, the exact returned `confirmation`, `previewToken` from `preview.token`, and the operator passphrase. Existing throttling and short-lived signed previews bind authorization to the owner and exact operation. The server returns a short-lived HTTP-only challenge cookie.
3. Send `step: apply` with operation, key, digest, epoch, confirmation and the same ledger. The server re-reads current evidence and reconstructs the digest before writing. An exact retry with the same cookie returns the committed receipt. A stale response requires a fresh preview and authorization.
4. To withdraw, repeat with `operation: withdraw` and omit the ledger. Preview binds the action to the active digest and epoch. Apply clears visibility and preserves both immutable versions and the MatchResults.

An approval uses the operator-reviewed ledger supplied in the preview. It records the exact selected edition and review evidence in the digest. Database ownership, source validity and the calculation are determined server-side. Ledger review is an operator judgment and remains an explicit prerequisite. Never put credentials or private notes in the ledger.

## Storage and consistency

| Document                                                           | Contents                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wrappedPublications/{editionId}`                                  | Scope, last version, operation epoch and active version/digest, or a null active pointer. The ID is a hash of the exact registered Team and tournament key.                                                                                                     |
| `wrappedPublications/{editionId}/versions/{digest}`                | Immutable private manifest, version, operator, approval time and audit reference.                                                                                                                                                                               |
| `wrappedPublications/{editionId}/projections/{version}`            | Immutable schema-tagged projection with scope, statistical coverage, overview, awards and omission reasons. Only version and sanitized projection cross the future public read boundary.                                                                        |
| `wrappedMatchDependencies/{matchId}`                               | One edition reservation and latest contributing version for this Team-specific Match ID. A correction that drops a Match leaves its prior reservation as a historical fence. Moving a reserved Match between editions requires a separately reviewed migration. |
| `adminActionChallenges/{challengeId}` and `adminAudit/{receiptId}` | Existing challenge and audit collections. Challenge consumption, the snapshot mutation and deterministic success audit commit together.                                                                                                                         |

The canonical digest covers the parsed edition ledger, exact projection, schema, algorithm, statistical policy, result generations and Firestore revisions of the scoped documents read during preparation. Missing point documents are represented explicitly. Canonical provider aliases are read through the retained Player and Coach records, and only direct reviewed targets are accepted. The manifest records revisions and paths rather than duplicating result bodies. Historical versions and projections are create-only. A used digest cannot be approved again after withdrawal or invalidation, and replaying a consumed challenge returns its receipt without reactivating anything. Version numbers increase only on approval. The epoch advances on approval, withdrawal and invalidation.

Reopen and result finalization use a bounded point lookup in the same transaction that changes the result. The lookup revokes a matching active version and increments the epoch. A concurrent approval either sees the revised source and fails, or commits first and is revoked by the result transaction. A failed result transaction leaves the projection unchanged. All future supported result deletion, withdrawal or replacement operations must call the same invalidation boundary in their transaction. Direct privileged Firestore edits bypass application safeguards and are outside the supported workflow.

For ledger, policy, canonical identity or alias corrections, withdraw the affected edition before applying the correction. Prepare and approve a new version against the changed evidence. In-progress approvals are fenced by the epoch and the source revision manifest. Production release still requires an operational owner procedure for these corrections and an audit of all result writers.

## Bounds and rollout

The owner endpoint accepts up to 256 KB of JSON and at most 64 fixture entries for one edition. Preview requests three scope point reads, one publication point read, two points per fixture (Match and current result), and one assignment point plus one bounded participant query per rated Match. Participant queries read up to 33 records and reject a 33rd. They are ordered by document ID through Firestore's default ordering and treated as complete only below the overflow sentinel. Identity resolution accepts at most 512 distinct source IDs per entity type, reads each source record and known alias once, and checks at most one target-record and target-alias lookup per source. Point reads use batches of 50, apart from the final approval dependency check of at most 64 points. The theoretical preview ceiling is 6,404 reads before retries, with actual edition cost driven by deduplicated identities and participant counts. There are no history scans, ballots or provider requests in Wrapped preparation.

Approval adds up to 66 reads over preview for the challenge, prior digest and dependencies. It writes five documents plus up to 64 dependencies. Withdrawal reads two documents and writes three. Result mutations add up to two point reads and one pointer write on local emulators. The gated public reader uses zero reads when disabled, one for an unavailable publication and two for an active projection, with no visitor-triggered calculation. Manifest and projection JSON are limited to 700 KB and 128 KB respectively. Oversized input or output fails explicitly. All new paths inherit the existing recursive client deny rule. Point reads and the fixture-local document-ID query require no composite indexes. See [Firestore transaction isolation](https://firebase.google.com/docs/firestore/transaction-data-contention) and [limits](https://firebase.google.com/docs/firestore/quotas).

Production needs separate authorization, actual edition and stages, a complete approved ledger per club, policy and editorial sign-off, licensed assets and the future presentation. Preserve client denial, deploy and verify invalidation in every supported writer first, then explicitly enable only the approved club and edition. Verify withdrawal and cache behavior before allowing traffic. No migration, backfill, index deployment or public route is required by Phase 2C itself.
