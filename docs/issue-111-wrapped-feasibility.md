# FutRate Wrapped · Phase 1 feasibility and design

Design proposal for [#111](https://github.com/jrodrguez08/rating_app/issues/111), audited against `master` at `96b7f87`. Wrapped is one collective recap per tracked Team and completed Apertura or Clausura. The same rules serve both clubs. This phase introduces no runtime feature.

Phase 2A implements the [local tournament ledger and coverage preview](issue-164-wrapped-coverage.md). Phase 2B implements [candidate statistics](issue-166-wrapped-statistics.md) under provisional award thresholds. Phase 2C adds the [local snapshot lifecycle](issue-168-wrapped-snapshots.md). Public delivery remains a proposal.

### Tournament boundary is the primary blocker

[`Match`, `Season` and `Competition`](../src/domain/models.ts) persist `trackedTeamId`, `competitionId`, `seasonId`, `kickoffAt` and provider/fixture identity. [Sync](../src/application/sync-football.ts) derives the Season ID from provider, competition and numeric provider season. Its optional dates and `isCurrent` describe provider season metadata. Standings target a current league season, and imported Match records carry no reviewed Apertura/Clausura stage, round, exact tournament membership or competition completion evidence. Neither kickoff month, calendar year, season ID, fixture status, nor the current standings target proves tournament membership. Cups, playoffs, rescheduled fixtures and season labels that cross years need explicit classification.

Require an owner-reviewed tournament definition backed by the authoritative competition calendar and completion evidence, including competition identity, season span, Apertura/Clausura edition and included stages. Prepare an explicit expected fixture ledger for each Team with evidence and an outcome for every entry. The provider fixture ID can help bind an entry, but the tracked Team's internal Match ID is authoritative. Approve regular season/playoff inclusion and any exclusions before computing results. A fixture may belong to only one approved tournament for a Team. An unmatched or ambiguous entry blocks approval. Use date ranges only to locate candidates for review.

## Candidate statistical contract

**Coverage first.** Require completed tournament evidence and a reviewed outcome for every expected fixture: valid rated result, finalized zero votes, or documented and owner-approved outside collection coverage/cancelled without replacement. A postponed fixture needs its final disposition, including an explicitly linked replacement if applicable. A closed Match with a missing, incompatible or invalidated result, an unresolved identity conflict, or a reopened/unfinished window in the in-scope roster blocks publication. An exclusion is disclosed and cannot be used to hide an unresolved in-scope result. Display rated matches over completed in-scope fixtures and disclose the number of reviewed exclusions/zero-vote Matches and coverage dates. If pre-launch gaps prevent a credible tournament recap, withhold it. Never imply every fixture was rated.

**Common validation.** Require canonical current summary path, matching Team and Match, authoritative completion, trusted effective close, `rating_closed`, and compatible current generation. Archived result revisions are audit evidence only. Validate finite averages in [1, 10], positive integer counts equal to the summary ballot count, and required participant/coach evidence where the story uses it. Fail closed on malformed data. Resolve reviewed aliases in a pinned input manifest. Count one row per canonical Player/Match. Collapse identical duplicates under existing projection rules, never double-count their votes, and block conflicting ratings or contradictory eligibility evidence. Preserve raw IDs and source versions in private provenance. Freeze presentation names and approved identity mappings in the released version.

**Proposed pilot thresholds for owner review.** Require at least three rated Matches and 30 valid ballots for the core recap. Community totals include all valid rated Matches, even low-sample ones. For comparative cards, define `Q` as the count of Matches with at least 10 valid ballots. Only these Match appearances enter comparisons. Every qualifying appearance has one equal weight in multi-Match means. This prevents high-traffic Matches from dominating an award. The per-appearance mean already weights each valid ballot equally. For deterministic ordering, propose recovering the integer sum from average × count if the nearest integer is safe and the residual is at most `8 × Number.EPSILON × max(1, |average × count|)`. If the tolerance reaches half a unit or the residual exceeds it, block the ambiguous value pending review. Use the reconstructed fractions for award means and comparisons. Round only for display. Show qualifying appearances and ballot counts next to awards, with a coverage note when they differ from community totals.

Never infer goals, assists, xG, minutes, lineups or turnout from ratings.

## Proposed architecture and cost controls

1. **Prepare offline.** Use the existing server-trusted club-to-Team resolution. Select the approved Team/edition ledger and retrieve exact Match references in deterministic chunks, then fetch only their current summaries. For optional awards fetch only the needed evidence. Resolve canonical Players and Coaches once per unique source with existing alias services. Run read-only preview and validate source ownership, reconciliation and completeness before any future production write. Exclude unexpected cross-Team paths even if they share an external fixture ID. Bound chunk size and transaction size explicitly in Phase 2. Cursor-based discovery, when authorized, uses existing Team/kickoff or document-ID ordering and a stable tie-breaker, with deterministic continuation until exhausted. Never use a hard limit as completion proof. The ledger point-read path needs no new composite index. Reassess indexes before introducing any tournament-filtered Firestore query.
2. **Build a repeatable candidate.** Define a reviewed tournament ID independent of localized label and route key. Use the existing club route convention with proposed `/{clubSlug}/wrapped/{tournamentKey}`, for example `2026-2027-apertura`, only after verifying the season label and edition against reviewed competition evidence. Bind the key to exactly one definition in the selected club. If multiple competitions would collide, reject the ambiguous key until a competition disambiguator is approved. Freeze algorithm/schema versions, sorted source references and revisions, alias mappings, coverage, rules, generated time and a digest. Store a compact public projection and a private provenance manifest. No ballot IDs, operator details or sensitive source evidence belong in the projection. Reject an oversized projection rather than truncating it silently.
3. **Approve and publish.** Future owner-only preview/apply must reuse existing authenticated, passphrase/CSRF-protected, idempotent audit patterns. Revalidate exact Team, edition, review digest, source generations and effective close in the apply transaction or a fenced equivalent. Bind active Match dependencies before exposure. Only the active pointer for this Team/edition exposes a projection. Publish the reviewed immutable version, active pointer and audit together, or stage a private immutable candidate then switch the pointer and audit atomically. Dry run writes zero. Apply estimates: one version, one pointer and one audit plus up to `M` dependency records if they are needed and any private manifest chunks. Account separately for revalidation reads, dependency lookups and retries. Never modify Match ratings or reuse a snapshot for another Team.
4. **Handle corrections explicitly.** The active snapshot must become unavailable if a contributing result is reopened, withdrawn, or materially invalidated. Phase 2 must wire the exceptional mutation to invalidate its Team/edition pointer atomically using a reviewed reverse dependency, and fence a stale preview from republishing. Treat approved alias changes affecting a released interpretation as a review trigger under the same contract. Preserve immutable versions and audit the reason, then require a new reviewed version to resume. No implicit leaderboard rewrites. Until the invalidation and concurrency contract is implemented and tested, public publication is blocked.
5. **Serve bounded reads.** Check the shared club availability gate and exact Team/edition. Prefer a compact active document holding the sanitized projection and version, costing **one point read** per fresh page or preview request, even for missing recaps. If pointer and projection must split, cap at **two** point reads with matching version and validity checks. No per-card reads, provider requests or public aggregation. Share page and metadata request-local reads where practical. Start with uncached active visibility so withdrawal is respected. Immutable version data can be cached behind the live visibility check. Any public static/CDN design requires demonstrated invalidation before adoption. Previously downloaded files and external crawler caches can outlive a withdrawal. Use canonical origin and club/tournament paths for share, and reuse explicit ES/EN and version parameters for social previews.

Illustrative capacity only: `M=24`, `C=24`, `U + A=75` gives about 123 point reads plus definition/ledger and revalidation. Checking 25 participant docs for each of 24 Matches adds about 600 document reads, plus optional evidence and Coach reads. Page batching lowers RPCs, not document count. Verify exact costs with SDK observations in Phase 2 and report index-entry and retry exclusions. Public load remains constant as the tournament grows.

## Roadmap and Phase 2 acceptance

1. **Owner decision.** Approve first target edition and qualifying stages, coverage/exclusion policy and sample floors, weighting and ties, optional XI/entrant/coach cards, availability and safe correction behavior, and presentation direction. Confirm approved photo rights, provisional Saprissa theme and neutral fallback. Authorize any separate production audit explicitly.
2. **Offline first.** Implement exact ledger and dry-run preview with a pure award calculator. Use synthetic fixtures for both clubs, including the same provider fixture with different Match IDs, ballots and coaches. Test calendar/season collisions, playoff and rescheduled fixtures, stable ties and ordering, missing/conflicting aliases, reused canonical Players, small samples, absent/malformed results, zero votes, reopen, missing positions, unused bench and coach changes. Verify invariance to input order and round only at display.
3. **Publication prototype.** Test owner authorization, stale/retried requests, atomic invalidation and monotonic version changes in emulators. Assert publication independence, bounded page/image reads, no ballot or provider reads, multi-page ledger traversal and correct cost accounting. Keep preview-only until the correction contract and each club's coverage pass.
4. **Presentation and release.** Implement the [storyboard](issue-111-wrapped-storyboard.md) using shared theme tokens and renderers. Test 320 px, keyboard, screen reader, reduced motion, long names, missing photos, ES/EN, share and fallback. Verify direct URL and image visibility with each club's flags and independent approval. Plan a separate release decision for each Team/edition.
