# Architecture

## Staged multiclub routing foundation

Phase 5 of Draft PR #143 passes the server-resolved `Club` into the shared podium and full-rating `ImageResponse` components. Their structural and accent colors come from `Club.theme`; rank medals, opponent badges, and semantic status colors remain independent. The neutral root icon uses no club palette. Public result, Story, and Open Graph routes call `requireActiveClub`, read the published result for that Team, check `Match.trackedTeamId`, and return no image for an unpublished or wrong-club Match. They make no provider request or Firestore write. Result page metadata resolves the language cookie, sets `es_CR` or `en_US` Open Graph locale, and publishes a scoped image URL with explicit `lang=es|en` and the result revision. Social-image routes resolve that query value independently of cookies, falling back to Spanish for absent, duplicate, or unsupported values. Titles, labels, dates, ratings, and image alt text use that locale; Story download filenames carry the club slug, Match ID, and locale. The 1200×630 Open Graph image and both 1080×1920 Story formats retain the existing canonical ranking, MVP, photo fallback, and publication rules.

`playwright.config.ts` launches the local Next server against `demo-rating-app-e2e` and the Auth/Firestore emulators. `tests/e2e/seed.ts` refuses nonlocal emulator hosts or any other project ID, creates separate Match contexts for shared fixtures, and adds Players, coaches, Team membership indexes, standings, and separate prepublished fixtures for visual coverage. The real voting-to-results test submits browser ballots to each club's open Match, inspects the persisted ballot and hidden result state, and uses `tests/e2e/finalize.ts` to invoke the canonical `AdminFootballSyncStore.finalizeMatchResult` at each Match's persisted close time. That helper also refuses any nonlocal emulator or project. It closes the two Matches independently and verifies their published summaries, pages, profiles, Studio, and Spanish/English images. Other browser tests exercise both themes, 320px layout, owner login, club-bound draft saves and Coach search, protected lineup and Coach preview/apply, and old/wrong-club routes. CI installs Chromium and Java and runs `npm run test:e2e` in its own job. Artifacts under ignored `test-results/` are review evidence, not deployed assets. No production credential or API-Football call is used.

Phase 4 of Draft PR #143 gives the single owner an explicit URL-backed club context under `/admin?club={slug}` and its detail/identity pages. The bare `/admin` and legacy detail URLs resolve to Herediano for compatibility; unknown or repeated slug values fail closed. The registry supplies the trusted Team ID and presentation theme. The five bounded dashboard queries, focused Match detail, Player membership search, and provider comparison use that Team. A detail first checks `Match.trackedTeamId` before reading its subcollections, so a shared provider fixture cannot mix the two tracked Matches or their drafts. A missing Saprissa Team displays a protected preparation state; page rendering does not bootstrap or synchronize it. Admin APIs require an explicit slug; every action must carry the matching Team ID before preview, authorization, apply, or receipt inspection. Existing Match-bound apply services continue to recheck persisted Team/fixture evidence transactionally. Player and Coach identity action hashes and challenge resources include the Team ID; older unscoped challenges cannot authorize the new action. Their deterministic success audits record the selected Team. Global canonical Coach and Player documents and immutable voting history remain global. Changing the URL mounts a separate admin workspace, so pending component state cannot become the other club's state. The exceptional result close/reopen command remains outside the web console behind its independent operator secret.

Coach discovery no longer orders a global newest-100 Coach sample and filters it afterward. Each Coach carries additive normalized name prefixes and Team association browse/search keys maintained by provider and verified assignment writes; a reviewed provider alias hides the duplicate identity from indexed discovery while retaining both documents and history. The owner-only `/api/admin/coaches` route validates the selected club, persisted Match Team, and fixture, then queries one 21-document index page for 20 candidates plus continuation. Team browse/search reads `teamBrowseKeys` or `teamSearchKeys`; the explicit unassociated path requires a name query and reads `unassociatedSearchKeys`. The Coach identity manual search uses the same indexed prefix model and can continue past unrelated clubs. Cursor scope, club, and query are bound together. Alias and canonical lookups add at most 20 direct reads each per page, so a page costs one index-state read, at most 21 Coach query reads, and at most 40 focused alias/canonical reads; repeated pages have stable document-ID ordering. These array-contains queries use Firestore's automatic single-field indexes, with no new composite index. A versioned `coachSearchIndex/state` completeness marker fails discovery closed until the additive offline backfill covers legacy Coaches, assignments, and aliases. Ordinary Match detail performs no global Coach query and directly reads only a currently assigned Coach for its summary. Search never supplies evidence or changes an assignment; preview, passphrase challenge, transactional apply, audit, and fixture checks remain authoritative.

The offline Coach backfill groups every Coach document by exact provider identity before processing reviewed aliases. Reconciliation can copy that identity to the chosen canonical document without deleting the old provider document, so both may legitimately share it. The reviewed alias alone chooses the canonical target; every other document carrying that binding has its discovery keys suppressed and a persisted hidden marker that later supported Coach writes preserve. Assignment, verified-assignment, and existing additive Team associations from all matching documents are unioned into the canonical index without changing historical references. A self-target alias keeps its Coach visible. Missing canonical targets, mismatched alias paths or provider bindings, and conflicting canonical bindings count as blocking issues; no complete marker is published for them. The backfill pages all four source collections and uses a provider-keyed in-memory lookup, giving linear reconstruction time and memory in the numbers of Coaches, associations, and aliases, followed by bounded 400-write batches. It marks the index incomplete before writing any batch and complete only after all batches succeed. Ordinary search retains its bounded read budget and never performs this historical traversal.

On the unmerged `feature/multi-club-support` branch, `src/config/club.ts` is the typed registry for the exact `herediano` and `saprissa` slugs. It binds each slug to a stable internal Team ID, display/short name, branding key, preliminary theme and public availability. `src/config/club-server.ts` resolves untrusted URL parameters on the server and returns 404 for unknown slugs. The public route tree is shared under `src/app/[clubSlug]`; `/` is only a club selector. No old global public route tree, redirect, rewrite or compatibility page remains.

The active Herediano pages pass the registry Team ID into existing indexed or bounded Firebase read services. Match detail, rate, result, player profile, Studio and image routes validate the selected club before reads; result and ballot services check Match ownership before returning data. All Saprissa data routes are unavailable before their read service is constructed, including images and overlays. Saprissa Home renders a localized coming-soon state without a Firestore or football-provider request. A slug never supplies a client-trusted Team ID. The ballot and vote-comparison APIs live at `/api/clubs/{clubSlug}/matches/{matchId}/...`; they resolve the configured Team on the server and reject an unrelated Match before a ballot read or write. The former unscoped API paths are absent.

`clubPath`, `matchPath`, `matchApiPath` and `playerPath` construct navigation, voting, WhatsApp, result, profile, Story, Studio and notification URLs from the selected club. Herediano's existing Match IDs and Firestore paths remain unchanged. New non-Herediano Matches use a deterministic hash of provider, tracked Team ID and fixture ID, so a shared fixture has separate Match subcollections, voting windows and results. Existing-ID updates reject a conflicting Team or provider fixture binding instead of overwriting it. Root metadata is neutral; each club-scoped page has its own canonical, Open Graph and Twitter URL, and `/[clubSlug]/social-card` uses that club's presentation colors. Shared result artwork now uses the selected club's palette, while the Saprissa public gate still withholds its data-bearing routes by default. The shared AppShell maps club primary, accent and focus tokens; Saprissa's preliminary `#6f2c91`/`#ffffff` values do not assert approved brand specifications.

Phases 1–5 in this Draft PR create no production Team document, index, alias, migration, provider mapping, provider request or production write merely by deployment. Public player history uses the existing indexed Team membership and paginated results read model; it discards a result whose parent Match has another tracked Team or a different Match ID. Phase 3 (#140) adds an explicit Saprissa bootstrap and independent scheduled operations, all disabled in production until the runbook's separate release steps. Phase 4 (#141) extends the one-owner admin console as described above. Phase 5 (#142) completes the shared presentation and local verification infrastructure; approval of exact Saprissa branding and any production preparation remains separate. Older global URL examples below document the currently deployed pilot and must be replaced in operational instructions at the final rollout.

The two internal synchronization endpoints retain an omitted `club` parameter as Herediano for existing GitHub secrets. A single exact `?club=saprissa` selects the Saprissa Team only when `SAPRISSA_SCHEDULED_ENABLED=true` on the server; other values and extra parameters fail closed. The existing Herediano GitHub jobs remain unchanged. Separate Saprissa jobs require the matching GitHub variable and endpoint URL secrets, run after the Herediano job even if it failed, and receive independent HTTP outcomes. Disabled Saprissa jobs do not start; a request reaching a disabled endpoint returns zero provider requests before constructing a provider or Firestore store. Each Team retains its own `footballSyncMetadata/{teamId}` discovery timestamp, execution lease, fencing, action and request count. Match-scoped capture attempts, participant reconciliation, coach assignment, voting windows and final results remain on the distinct Match paths. Standings remain `standings/{teamId}`. There is no provider-response sharing across clubs: shared fixtures are requested once per enabled Team discovery and are persisted as two independent Match IDs.

`SAPRISSA_PUBLIC_ENABLED=true` is a separate server-side exposure gate. Its missing, false, or malformed value leaves the coming-soon Home and all data-bearing routes inaccessible through the shared `requireActiveClub` boundary, including direct API and image URLs. It does not change historical Match data. Herediano remains active regardless of Saprissa flags. The authenticated health endpoint reports disabled, bootstrap-required, no-relevant-fixture, awaiting-evidence, and last-execution-failure states without provider calls. Lifecycle completion stores a Team-scoped failure boolean alongside the existing action: a transport, malformed-provider, persistence, or evidence-conflict failure can retain `preparing_rating` or `refreshed` as its action, while typed `lineup-unavailable`, `lineup-incomplete`, and `coach-missing` conditions are expected evidence waits. A completed attempt with no operational failure clears the boolean; a skipped live capture after an unresolved operational error retains it through cooldown or the retry ceiling. Health checks that outcome before treating a Team-bound preparing Match as healthy evidence wait. These flags are release controls, not Team or voting state; existing active windows continue under their persisted timestamps if scheduled work is disabled, but automatic close waits for a later trigger or the established exceptional operator path.

Saprissa bootstrap is an explicit production-guarded operator command, never an app startup task. It performs one exact-name/country provider identity lookup before its Firestore transaction, compares the returned ID with the operator's reviewed ID, rejects a provider mapping already assigned to another Team, and validates every canonical Saprissa Team field. Dry run reads only; confirmed apply creates the Team or fills its missing provider ID and is idempotent. It does not touch Herediano. Existing membership-index backfill supports `--team-id deportivo-saprissa`; it is a later explicit additive operation after fixture/participant ingestion and before public Player access. The existing declared indexes serve both Teams. This design adds no ordinary HTTP collection scan, index, service or paid scheduler. Current lifecycle `listMatches(teamId)` and standings target selection still read all persisted Matches for that one Team; monitor that Team-scoped read volume and introduce a reviewed indexed projection before it becomes large rather than treating a bounded sample as complete.

## Application shape

Administrative Player search uses the maintained Team membership read model: one completeness-marker read, one indexed 21-membership page for 20 choices, then bounded batched Player, provider-alias and distinct canonical-target reads. A full provider-backed page normally estimates 62 document reads, with an 82-read ceiling when every choice needs a distinct canonical-target lookup; an empty result costs two minimum reads. It performs no transaction, provider request, write or exhaustive fallback. The owner-only route's best-effort `admin.player_search` event records query/page/read estimates and duration without query text, identity data or Firestore logging writes. Estimates cover successful repository observations, not failed-RPC billing, index-entry charges or Auth service calls.

The lineup picker debounces all queries by 200 ms, including empty browse, using shared domain normalization. Its request effect depends on primitive club/query state rather than the selected-Player Set. It retains raw loaded choices and derives selection filtering during render. A club/query key scopes visible results and continuation; shared AbortController ownership plus post-body signal checks fence both first-page and pagination responses. Existing club/Match React keys still reset the workspace. No cross-request or persistent cache is added, and authoritative mutation services still reload identities. [The search investigation](docs/issue-155-player-search.md) distinguishes measured request savings from the inconclusive daily quota attribution and the [Home, admin detail and catalog read optimizations](docs/issue-155-firestore-reads.md).

Next.js App Router and strict TypeScript form the web application. Pages and layouts are Server Components by default; use Client Components only for browser state or interaction. Tailwind CSS consumes semantic tokens. Domain types and ports do not import Firebase or React.

Public metadata uses native App Router APIs and metadata routes. `src/config/site.ts` is the single canonical origin and public identity source: `NEXT_PUBLIC_SITE_URL` may replace the explicit `https://www.futratecr.com` fallback, while arbitrary request and Vercel Preview hosts are never consulted. Root Open Graph/Twitter metadata, the manifest, generated Apple icon, scalable browser icon, and deterministic 1200×630 `/social-card` image require no Firebase, provider, authentication, or request-time data. The social card uses an ordinary route instead of automatic social-image file metadata so `metadataBase`, not the request host, controls its absolute URL. A pure shared builder gives ordinary public pages their own canonical and complete Open Graph identity because Next.js shallowly replaces nested metadata objects. Static Partidos and Jugadores metadata supplies focused titles and descriptions; match and player routes construct identity from encoded route parameters.

A published result route is the focused exception to metadata-only reads. It reuses `AdminResultService`'s current result visibility guard, then builds one shared podium projection from the immutable summary. The projection preserves the public ranking order (`average desc`, persisted participant order, stable Player ID), maps the persisted MVP IDs independently, and resolves reviewed Player aliases through bounded direct reads of only the result Players, their deterministic alias documents, and any distinct canonical Player documents. The explicit football-result safety limit is 30 rated Players; an invalid larger summary exposes no sharing projection. Within that limit, identity reads are at most 30 source Players, 30 deterministic aliases, and 30 distinct canonical Players, with no query or pagination claim. The result page, metadata, 1200×630 Open Graph image, 1080×1920 podium Story, and 1080×1920 full-ratings Stories consume that same projection. The table paginator allows at most 16 rows per image and balances larger results deterministically across the minimum page count while preserving the projected order, rating precision, and MVP flags. They never query ballots, participants, provider APIs, or an exhaustive collection. A result with no valid rated Players, a missing score, a reopened window, a pending summary, or an incompatible summary receives neutral non-indexed metadata and no dynamic image.

The public Studio routes reuse that exact projection and visibility guard. `AdminStudioService` performs one collection-group query for at most 20 `final` summaries belonging to the configured Team, ordered by immutable `generatedAt` descending, then one bounded batch of at most 20 parent-Match reads. This is an explicit product limit for the match selector, not a completeness claim. It requires the declared `results(teamId ASC, status ASC, generatedAt DESC)` collection-group index. A directly addressed eligible published Match outside that selector window may still render and is prepended to the selector for that request. `buildStudioMatchPresentation` derives the podium, full ranking, highest and lowest Players, coach rating, ballot count, and unweighted arithmetic mean of published per-Player match averages without another persistence source. The interactive `/studio` client owns one view state shared by its ordinary and fullscreen tab controls; the fullscreen element reserves a compact toolbar and scrollable board area, so switching views neither exits fullscreen nor remounts or changes the selected Match. `/studio/overlay/{matchId}` renders the podium view without application navigation or controls and rechecks the same configured-Team and published-result boundary. Studio reads no ballot, participant, provider-observation, or provider API data and performs no write.

The public image routes are dynamic Node routes with `no-store` responses. Match metadata uses the configured origin for absolute canonical and image URLs and versions the Open Graph URL with the immutable result generation timestamp. External Player portraits are fetched only from the existing exact HTTPS API-Sports player-image allowlist, with redirects rejected, a three-second timeout, image content-type validation, and a two-megabyte limit; every failure becomes the deterministic initials fallback. Story responses use an attachment filename by default and an explicit inline disposition for the ordinary user-activated view link. Full-rating pages use `/matches/{matchId}/results/story/table?page=N`; missing page defaults to one, while malformed and out-of-range pages fail closed. Their filenames include the deterministic page and total count. The browser does not fetch a file before invoking a native share or open a delayed pop-up. Image generation is read-only and introduces no collection, index, migration, credential, scheduled work, or paid provider request.

The Home-only WhatsApp action uses that same canonical origin to build an encoded `/{club}/matches/{matchId}/rate` deep link. Its pure URL helper never reads an incoming or Preview host and adds no voter, ballot, provider, diagnostic, or tracking data.

The resolver's default environment explicitly reads `process.env.NEXT_PUBLIC_SITE_URL` so Next.js can inline the same build-time value if bundled for the browser. Passing the entire `process.env` object through an alias would leave browser consumers using the fallback. Current Home WhatsApp links, result share/copy props, Story download/view links, versioned social metadata, PNG hostname text and Studio overlay URLs are generated server-side; browser controls consume those supplied URLs. Preview deployments also advertise this canonical origin; changing the public environment requires a new build. Notifications intentionally require an explicit valid HTTPS origin and omit the link on missing/invalid configuration, preserving non-blocking delivery. They never adopt a request host or the public fallback. See the [domain audit and regression coverage](docs/issue-158-canonical-domain.md).

`src/config` selects the initial club presentation. `src/domain` describes stable business concepts and provider-neutral ports. `src/lib/firebase/browser.ts` lazily initializes one shared web SDK app and derives Firestore and Auth from it only when called and configured. Local mode always connects both services to their explicit emulators and never falls back to a cloud project. Development and production modes require complete Firebase Web configuration. Explicit local scripts use the emulator's REST API; the internal server route lazily initializes Firebase Admin from server-only environment credentials for trusted development/production writes. No Admin object or credential enters browser modules.

Presentation uses semantic game tokens for structure and CSS custom properties for club primary/secondary colors. `AppShell` maps the selected `TeamPresentation.theme` into those properties at the presentation boundary; generic components never depend on Herediano-named colors. Tailwind utilities consume the tokens, while a small set of global conventions supplies crisp panels, status badges, controls, and hard shadows. This changes presentation only and does not localize or duplicate domain data.

## Internationalization

Exactly `es` and `en` are defined in `src/i18n/config.ts`; `es` is the default and fallback. Server Components resolve the `rating-app-locale` cookie on each request. Missing, malformed, and unsupported values resolve to Spanish. The root layout uses the same result for localized metadata and `<html lang>`. A small Client Component renders the language switcher, persists a one-year same-site cookie, and calls `router.refresh()`; it receives its initial locale and labels from the server and does not own a competing locale default.

Routes remain stable and locale-neutral (`/`, `/matches`, `/players`, `/standings`, `/studio`, and their detail routes) because the current application does not need locale-specific URLs or duplicated route trees. Message resources are bundled TypeScript objects under `src/i18n/messages`; the English resource is statically checked against the Spanish canonical shape, with a runtime alignment test. Translation lookup does not perform network requests. Product-facing dates and numbers use centralized native `Intl` helpers with `es-CR` or `en-US` and Costa Rica display time where appropriate; persisted timestamps remain UTC.

Public Home, archive cards, and Match detail evaluate `getVotingWindowState(match, now)` once per presentation against the validated `getEffectiveVotingWindow(match)`. Only `active` renders the ballot boundary and effective close; a reopened window therefore uses its persisted effective close rather than the original audit timestamp. The shared deadline formatter always uses `America/Costa_Rica`, while localized text explicitly names Costa Rica. Future, expired, and invalid windows use distinct truthful presentation states without timers, polling, extra reads, or device-timezone dependence.

Translations cover presentation labels only. Provider/domain names—including teams, competitions, players, and coaches—remain authoritative proper nouns and are not copied into localized persistence fields. Locale selection and club theme are independent.

## Proposed Firestore model

Top-level collections use generic IDs:

```text
teams/{teamId}
teams/{teamId}/playerMemberships/{playerId}
teams/{teamId}/playerMembershipIndex/state
competitions/{competitionId}
seasons/{seasonId}
players/{playerId}
playerProviderAliases/{aliasId}
playerIdentityReviews/{reviewId}
coaches/{coachId}
coachProviderAliases/{aliasId}
coachIdentityReviews/{reviewId}
matches/{matchId}
matches/{matchId}/participants/{playerId}
matches/{matchId}/coachAssignments/head-coach
matches/{matchId}/verifiedCoachAssignments/head-coach
matches/{matchId}/verifiedLineups/current
matches/{matchId}/lineupDrafts/{ownerUid}
matches/{matchId}/lineupReconciliations/provider
matches/{matchId}/providerObservations/api-football
matches/{matchId}/finalWhistleAttestations/manual
matches/{matchId}/ballots/{voterId}
matches/{matchId}/results/summary
matches/{matchId}/resultRevisions/reopen-{sequence}
players/{playerId}/matchSummaries/{matchId}
players/{playerId}/statistics/{seasonOrCareerId}
standings/{trackedTeamId}
```

The original `ratingReadyAt`, `votingOpensAt`, and `votingClosesAt` fields remain the first-window audit record. An exceptional reopen adds `votingReopenedAt`, monotonic `votingReopenCount`, and the current `effectiveVotingOpensAt`/`effectiveVotingClosesAt`; ordinary matches continue to use the original bounds. `votingClosedEarlyAt` records an operator close. Provider synchronization preserves all of these lifecycle fields.

`votingOpeningMode` records whether the first window came from provider-confirmed lifecycle readiness or the manual final-whistle operation. The shared manual-status guard permits `scheduled`, `live`, and `finished`, allowing independent final-whistle evidence to bridge provider delay, and rejects `postponed`, `suspended`, `cancelled`, and `abandoned`. Preview and apply both use the guard, while apply evaluates the freshly read Match inside the same Firestore transaction as every resulting write. Provider Match upserts also read and preserve lifecycle fields transactionally, so a concurrent status refresh and manual apply serialize: an ineligible status observed first rejects opening, while a committed manual window observed first remains authoritative. A manual opening atomically creates `finalWhistleAttestations/manual`, stores `manualFinalWhistleAttestedAt`, and establishes the same immutable original voting timestamps. The attestation binds the Match, tracked Team, provider fixture, operator, HTTPS evidence, reason, observed provider status, and trusted server time without fabricating provider `FT`. Close, notification, aggregation, archive, and reopen accept that durable attestation as final-whistle authority while voting and eligibility keep their existing rules. Later provider synchronization preserves the mode, attestation timestamp, and window.

`AdminManualVotingService` is the sole manual-opening mutation boundary. Preview and apply read the authoritative verified lineup and its materialized participants, canonical Player documents, verified coach and assignment, reconciliation receipt, protected ballots/results/revisions, and existing attestation. Apply consumes the exact short-lived challenge and creates the attestation, Match transition, notification state, and deterministic success audit in one transaction. It performs no football-provider request. Exact retries return the stored audit plan without repeating writes.

The Match detail loads the bounded canonical coach roster and exposes the existing `AdminVerifiedCoachService` flow for scheduled, live, or finished Matches whose rating state remains mutable. Coach verification itself never attests final whistle or advances lifecycle state. Existing ballots, results, revisions, a voting window, or incompatible identity evidence still reject the transaction.

Each original or reopened window also has one server-owned operator-notification generation. `votingOpenNotificationWindow` uses `0` for the original window and the monotonic reopen count afterward. Status, attempt, lease, first-attempt, sent timestamp, and provider-message fields live on the Match so concurrent lifecycle or operator processes can transactionally claim one send and later retries can observe its durable outcome. Provider synchronization preserves these fields. Ballots, voters, and aggregate data are never notification inputs.

`matches/{matchId}/resultRevisions/reopen-{sequence}` is an operator-owned, server-only immutable snapshot of the former `results/summary`. It retains the complete result, its original `generatedAt`, archive time/reason, revision number, and the window that produced it. Reopen creates this revision, deletes the current summary, and transitions the match to `rating_ready` in one transaction. The deterministic current summary is therefore absent and unpublished while the effective window is active. No query index is needed because revisions use deterministic document reads; existing deny-all client rules already protect them.

The implemented `teams/{teamId}` document contains `displayName`, `shortName`, `countryName`, `countryCode`, `brandingKey`, optional `externalProviderId`, and Firestore `createdAt`/`updatedAt` timestamps. `club-sport-herediano` is the stable initial ID. The seed JSON is the canonical basic Team data; presentation configuration derives its identity and names from that record while keeping theme colors in source code. Firestore snapshots are converted and runtime-validated at the persistence boundary before becoming domain `Team` values.

`standings/{trackedTeamId}` stores one ordered, provider-neutral league snapshot with its internal Competition/Season identity, provider competition/season identity, normalized rows, and provider-sync timestamp. The target is derived from persisted tracked-Team matches joined to a current league Season; it is not hardcoded in the page. A daily trusted sync makes exactly one `GET /standings?league=...&season=...` request and replaces the document atomically only after the entire collection validates. Empty, malformed, or failed responses leave the previous snapshot untouched. `/standings` reads this document only through Firebase Admin, so page views are provider-free and client rules remain deny-all for this collection. No index is required for the direct document read.

An explicit emulator-only script ensures the initial document exists. It requires a local emulator host and a `demo-*` project ID, creates only when absent, and only adds a missing `countryName` to a pre-milestone record. It never runs during application rendering or startup.

A match stores tracked team, its stable provider Team ID, opponent, home/away snapshots, competition, season, kickoff, status, score, provider fixture ID, confirmed goal-event snapshots, optional live elapsed minute, and voting bounds. `Match.id` is always the physical `matches/{matchId}` document ID: persistence writes omit a duplicate payload ID, and snapshot hydration treats the document path as authoritative if a legacy payload contains a stale `id`. Archive, detail, result, ballot, lifecycle, and player-history paths therefore share one durable identity without requiring a data migration. The provider score remains canonical; malformed or incomplete goal incidents are ignored instead of inferred. A durable Player stores provider-mapped identity and current name/position metadata in `players/{playerId}`. A match participant at `matches/{matchId}/participants/{playerId}` explicitly stores internal and provider Team IDs alongside the historical name, number, position, squad role (`starter` or `substitute`), `participated`, and optional confirmed entry/exit minutes. Global Player records never contain match participation or permanent club membership. The tracked Team's head coach has durable identity in `coaches/{coachId}` and one match-specific `matches/{matchId}/coachAssignments/head-coach` document with the same explicit Team ownership; the fixed assignment path models the single rateable coaching role without modeling a full staff. Coach records distinguish `provider` and `operator_verified` identity provenance. Provider identity fields remain optional only for an operator-verified coach and must be a complete real provider pair when present. The server-only `verifiedCoachAssignments/head-coach` audit record binds one verified Coach to the internal Match, tracked Team, provider fixture, HTTPS evidence, reason, operator context, and verification timestamps. Ballot selection requires `participant.teamId == match.trackedTeamId && participant.participated == true`. For the current configuration this selects only confirmed Club Sport Herediano participants and its head coach; opponent players and coaches remain outside MVP rating scope. A future club changes the tracked Team data, not this logic.

`teams/{teamId}/playerMemberships/{playerId}` is a server-owned search read model, not participation or eligibility evidence. Current squad sync, tracked-Team MatchParticipant persistence, verified lineup apply, and a fixture-bound finalized-Match provider observation upsert canonical identity, normalized canonical and historical name prefixes, available presentation metadata, provenance, and first/last observation timestamps. Membership survives transfers, while only explicit tracked-Team evidence can create it; operator-verified provenance is not weakened by a later squad or provider observation. A provider observation membership is affiliation and discovery evidence only and never establishes participation. Shared application policy builds and merges this evidence and resolves reviewed aliases for offline and online consumers.

The exhaustive discovery service is restricted to the explicit audit/backfill command. It pages all current-Team Players, tracked-Team Matches and participants, fixture-bound verified lineups, reviewed aliases, and existing memberships; validates bindings; excludes opponents; and creates additive canonical repairs. A successful apply writes `playerMembershipIndex/state` only after every membership batch completes. Online reads require its current schema marker and fail explicitly when it is missing or stale. Admin search performs one 21-document indexed membership query per 20-item page, then bounded Player and alias lookups; its document-ID cursor is deterministic across repeated searches and duplicate aliases. Public history pages the membership index and only final result summaries for the Team, then batch-reads their parent Matches. Its reads scale with indexed Players plus published rated Matches, never with total Matches, participants, drafts, or verified snapshots. The public service rejects a published result identity absent from the complete membership index, preserving public/admin identity parity. The declared `results.teamId` collection-group index supports the public result query.

`matches/{matchId}/lineupDrafts/{ownerUid}` stores the authenticated owner's non-authoritative preparation with Match/Team/provider-fixture binding, participant arrangement, a monotonic version, content hash, and trusted timestamps. Saves permit incomplete lineups, validate every canonical Player against current Team, historical membership, selected-match evidence, or the prior draft, and reject protected voting/result states. Compare-and-set versions reject stale edits; an exact lost-response retry returns the prior receipt. Draft persistence never writes MatchParticipants, VerifiedLineupSnapshot, lifecycle fields, ballots, or results. Verified apply deletes the owner's draft inside its existing atomic challenge/mutation/audit transaction.

`matches/{matchId}/lineupReconciliations/provider` stores one durable fixture-bound provider comparison status and aggregate count. Comparison runs after provider aliases resolve and uses canonical Player identity, starter/substitute role, and participation facts rather than counts or names. Complete compatible evidence records `matched`; a strict subset, unresolved internal-only identity, or unknown participation records `provider_partial`; provider lineup absence records `provider_missing`; extra or different identities, duplicate canonical identities, role disagreement, or contradictory confirmed participation records `conflict`. Persistence is transactional and idempotent: missing or partial retries cannot overwrite an established matched or conflict receipt, a stronger partial can replace missing evidence, and later complete matched or conflicting evidence may replace an earlier conclusive result. The receipt contains no raw provider payload and never weakens verified snapshot precedence.

A completed ballot is one compact document containing `matchId`, `teamId`, `voterId`, a map of player IDs to integer ratings, one `{ coachId, rating }`, and a server timestamp. Its document ID is the verified Firebase UID inside the match's `ballots` subcollection. A trusted Next.js server endpoint verifies the Firebase ID token and derives that UID; the payload cannot select its owner. A Firestore transaction reloads the authoritative match, participants, head coach, and ballot, validates the active server-controlled window and exact eligible ID set, then creates only if absent. Direct client reads and every client write remain denied by rules. This deterministic path plus the transaction enforces `one voter + one match` without a per-score write explosion.

## Aggregation and results

The existing lifecycle trigger finalizes results when trusted server time reaches `votingClosesAt`; no second scheduler or provider call is involved. `AdminFootballSyncStore.finalizeMatchResult` reads the authoritative tracked-Team participants, deterministic head-coach assignment, and private ballots in one Firestore transaction. Existing summaries early-exit without changing `generatedAt`; finalized summaries are immutable in the MVP. Raw sums are divided by the valid ballot count and unrounded numeric averages are stored; presentation consistently rounds to one decimal. One ballot is sufficient, zero ballots creates an explicit `no_votes` summary, and every exact top-average player is stored in ordered `mvpPlayerIds`. Coach results remain separate and never enter MVP ranking. Ranked ties use canonical participant order, then stable player ID.

The pilot reads all ballots once at close, which is appropriate for the small community. The aggregate DTO and UI do not depend on the query strategy, leaving a replacement boundary if volume grows.

## Authentication and security

Voting-window recovery uses only the local production CLI. It requires valid production Firebase Admin credentials for an explicitly repeated project ID and a separate high-entropy operator token. It creates or validates the Coach and deterministic verified assignment together; repeated identical application is a no-op and any identity, evidence, or binding conflict aborts. Direct clients remain denied by the existing recursive Firestore rule.

Reopen dry-run and apply use the same transaction reads and validation. Apply verifies finished/closed state, a current result, auditable timestamps, current participant/coach/ballot consistency through canonical aggregation validation, a bounded requested close time, and a collision-free revision path before any write. Early close reads Firestore's server-assigned document read time, queries ballots inside the finalization transaction, rejects an existing current summary, and invokes the same `aggregateMatchResult` path as scheduled finalization. Firestore transaction retries ensure a concurrent ballot is either committed before the close and included, or observes the closed state and is rejected.

Home and Partidos reuse the same client `BallotEntry` boundary only while a persisted match window is active. Firebase Anonymous Authentication now establishes low-friction voter identity in the browser. The root layout keeps server rendering intact and mounts a zero-UI Client Component that calls the focused auth boundary. That boundary waits for Firebase Auth initialization, reuses `currentUser`, shares concurrent first-load work, and signs in anonymously only when needed. Local mode connects Auth to `127.0.0.1:9099` once per app, including across Fast Refresh, while development and production never connect to the emulator.

Firebase UID is the canonical `voterId`. Ballot operations cross the trusted server boundary because exact eligibility depends on a dynamic match-participant set that should not be duplicated in browser rules. Authentication is not authorization: current rules grant no match, lifecycle, participant, coach, sync-metadata, or ballot access to an anonymous user. The server endpoint alone verifies identity and authorizes ballot status/submission. Team documents remain public-readable and client-write-denied.

Anonymous identity is device/browser storage identity, not verified person identity. Clearing storage, using incognito, another browser/device, or creating another anonymous account can bypass person-level uniqueness; fingerprinting is intentionally excluded for the initial small supporter group. Future Firebase provider linking can upgrade an anonymous account while preserving its UID where supported. Automatic anonymous-account cleanup is not assumed. App Check is a future public-launch abuse-hardening option, not part of this foundation.

Never expose Admin credentials or raw voter UIDs in normal UI. Public Firebase web configuration is not secret, but belongs in environment-specific files. Use separate development/production projects and Auth/Firestore emulators for local work. Validate App Check and abuse controls before public launch.

An extra or different identity, duplicate canonical identity, role disagreement, or positive participation claim against manually unused/unconfirmed evidence is a conflict and causes the entire context write to fail. Provider data does not silently downgrade or replace verified provenance. This precedence is `operator-verified fixture evidence`, then compatible persisted provider context, then compatible new provider evidence. It does not bypass missing fixture, wrong Team, malformed provider data, or coach validation.

Each lifecycle execution builds an ordered, compact operational trace and emits the same sanitized entries to server logs and the authenticated lifecycle response consumed by GitHub Actions. The trace covers match selection, fixture refresh and normalized status, lifecycle phase, focused lineup/player/event response structure, aggregate participation reconciliation, readiness blockers, voting/finalization decisions, final action, and provider request count. It contains only stable identifiers, states, scores, structural presence, and aggregate counts—never credentials, authorization data, voter or ballot data, player-level payloads, or raw provider responses. Observation is best-effort and cannot change control flow, provider request count, persistence, readiness, or voting timestamps.

Local sync persistence remains restricted to a local Firestore host and `demo-*` project. Trusted hosted lifecycle and ballot operations use Firebase Admin with explicit server credentials. Browser rules continue to allow public Team reads and deny all client access to matches, lifecycle fields, participants, coaches, sync metadata, and ballots; Home and ballot routes read their context on the server.

## Match lifecycle and scheduling

Provider-neutral fixture `status` and the Rating App `ratingState` (`not_ready`, `preparing_rating`, `rating_ready`, or `rating_closed`) are separate Match facts. Focused refresh time, successful participant/readiness time, and voting bounds are compact server-controlled lifecycle fields.

The observed post-match delay has three independent sources: the external trigger may wait up to the approximate 30-minute workflow interval plus GitHub queue delay; the next focused fixture read must first observe provider `FT`; and final lineup/player/event evidence may still be unavailable or conflicting after `FT`. A complete operator-verified fixture baseline removes the provider evidence-publication wait, but it does not remove the need for another lifecycle execution. GitHub scheduled workflows cannot provide a dependable five-minute cadence, so the 30-minute workflow remains the no-cost fallback and the authenticated owner console supplies the bounded prompt trigger for the selected live or recently finished match.

The lifecycle service first reads persisted matches and, before discovery or refresh, selects any expired `rating_ready` match as pending finalization work. That work outranks active windows, live, preparing, scheduled, and historical fixtures until its persisted ballots aggregate successfully; it uses zero football-provider requests, and a failure remains retryable at the same priority on the next trigger. Otherwise fixture discovery is decided only from the persisted `lastFixtureDiscoveryAt` 12-hour interval. A known scheduled, live, or closed Match cannot suppress that periodic check; successful empty responses still advance the timestamp, while provider failures do not. After any due discovery, operational selection gives established windows priority, then mutable live matches, recently finished/preparing matches, and the earliest relevant scheduled match. Terminal `rating_closed` history is only an operational fallback and cannot displace a new scheduled fixture. Presentation uses a separate public selector: an active effective voting window, a genuinely current live fixture within four hours of kickoff, the nearest scheduled fixture (including the existing four-hour post-kickoff grace), then the newest completed historical fallback. Historical provider status is not rewritten merely to influence presentation. Matches beyond 24 hours early-exit; within 24 hours they refresh no more than every six hours, within two hours no more than every 15 minutes, and live/preparing matches refresh whenever the external trigger runs. Postponed/suspended fixtures retry conservatively; cancelled/abandoned fixtures never create a window.

Provider final status alone never opens voting. A finished fixture moves to `preparing_rating`; focused final participant reconciliation must succeed over trusted provider evidence or a compatible operator-verified baseline, at least 11 tracked-Team participants must be rateable, and the deterministic fixture-specific head-coach assignment must exist. Only then does the service set `ratingReadyAt`, `votingOpensAt`, and `votingClosesAt` two hours later. Existing timestamps always win on repeated runs. Manual preparation never writes those fields. Failures leave the match retryable and unopened; terminal rating states do not regress on transient provider status.

The first lifecycle refresh that normalizes the provider fixture to `finished` stores immutable `finishedObservedAt`; this is the trusted observation time, not an inferred final-whistle timestamp. `participantSyncedAt`, `ratingReadyAt`, and `votingOpensAt` provide evidence and opening endpoints, so the owner console can calculate evidence reconciliation and confirmed-FT-to-opening delays without inventing provider publication time. `footballSyncMetadata/{teamId}` records the last execution source, start, completion, outcome, selected match, and provider request count.

Scheduled and owner-triggered calls enter `runConfiguredLifecycle`. A transactional five-minute lease in `footballSyncMetadata/{teamId}` admits one execution and makes overlapping calls return before constructing a provider request. Provider calls have a ten-second bound and renew the matching lease before each read; target selection records the Match on that attempt. Completion clears only the matching attempt, stores its attempt ID and sanitized metrics, and cannot release a replacement lease after stale takeover. The owner flow additionally reloads the exact Match, verifies the canonical lifecycle selection and Team/fixture binding, accepts only live or recently finished unopened states, consumes a one-use passphrase challenge, writes one deterministic authorization audit, and rate limits accepted requests to one per Match per minute.

The same authorization transaction creates `adminLifecycleRequests/{auditId}` with a status separate from Match `ratingState`: `requested`, `running`, `skipped_busy`, `completed`, `failed`, or `voting_open`. The exact consumed challenge remains the credential for status checks and bounded recovery for ten minutes. A request allows at most five claims and three provider executions, with short server-controlled backoff after a busy lease or transient failure. `running` has its own short lease so a lost HTTP response can be recovered. Busy reconciliation records the observed shared lifecycle attempt and only adopts its completion when both attempt and Match agree; otherwise expiry becomes a retryable failure. The owner UI checks status only on explicit operator action. It never writes Match lifecycle state or voting timestamps; the canonical service performs every selection, `FT`, participant, coach, and window check, and `voting_open` requires the persisted active window.

After the window transaction succeeds, trusted server code claims the corresponding operator-notification generation and sends one concise email through Resend. The deterministic provider idempotency key is `voting-open/{matchId}/{windowSequence}`. A short Firestore lease serializes concurrent attempts; unsuccessful delivery returns the generation to `pending`, and later lifecycle runs retry it. Successful delivery records `sent` and suppresses repeats. If a provider response is ambiguous, the same key is reused only inside Resend's documented 24-hour retention period; after 23 hours the generation reports `manual_review` instead of risking a duplicate. Missing configuration and all provider/persistence errors emit sanitized `voting.notification` logs and never prevent, close, or extend the voting window. The same service runs immediately after a successful operator reopen.

A private GitHub Actions workflow runs every 30 minutes and performs only an authenticated `POST` to `/api/internal/match-lifecycle`; it does not check out or install the repository. Missing deployment secrets make scheduled runs exit successfully without calling anything. This uses existing GitHub/Vercel capacity and adds no separately billed scheduler, worker, queue, or always-on service under the current usage assumption; actual plan consumption must still be monitored. `CRON_SECRET` protects the endpoint with constant-time bearer comparison. Vercel holds API-Football and Firebase Admin credentials, while GitHub needs only the endpoint URL and matching cron secret.

A separate private workflow calls `/api/internal/standings-sync` once daily at `09:00 UTC`, equivalent to `03:00 America/Costa_Rica` year-round. It shares the authenticated server boundary but not lifecycle polling, and emits only compact sanitized standings outcomes and counts. GitHub additionally holds `STANDINGS_SYNC_URL`; no provider or Firebase credential is added there.

Controlled live verification on 2026-08-29 discovered API-Football fixture `1551672` (CS Cartaginés vs CS Herediano, 2026-08-30 17:00 UTC) and then refreshed that persisted fixture with exactly one focused provider request. The lifecycle remained `not_ready` with no voting timestamps while the provider status was scheduled, confirming that an away fixture is selected without opening a window early.

Home reads relevant Match data through the server-side Admin boundary, so client Firestore rules remain unchanged. Without Admin configuration or a relevant persisted match, Home retains the honest empty state. With data, a localized scoreboard panel shows upcoming, live, rating-ready, or finalized context. Public selection uses the effective-window and bounded-recency rules above rather than operational lifecycle priority. An active rating-ready match links to `/matches/{matchId}/rate`; a finalized match links to `/matches/{matchId}/results`. Both server routes fail closed and expose only their focused sanitized DTOs.

## Multi-team scaling

Every match references a tracked `teamId`; community and theme configuration selects the current context. Collections, indexes, rules, and aggregates remain generic. This supports another club without premature tenant administration or separate schemas.

## Owner console security architecture

The owner console uses the existing Firebase project and email/password provider, with no in-app registration. A named `rating-admin` browser app uses in-memory persistence so signing in never replaces the default app's persistent anonymous supporter. The ID token is checked server-side with revocation enabled, exact `ADMIN_OWNER_UID`, verified email, and password-provider claims before a one-hour Firebase session cookie is issued. Every admin read and mutation rechecks that revocation-aware HttpOnly, Secure, SameSite=Strict cookie. Mutations additionally require an exact configured Origin and a double-submit CSRF token. Login replaces prior admin cookies; logout revokes owner refresh tokens and clears the session, CSRF, and action cookies. Admin pages and APIs are dynamic/no-store, unlinked, and non-indexed.

Sensitive web mutations require `ADMIN_PASSPHRASE_SCRYPT`, independent from Firebase credentials and the CLI operator token. Node's built-in scrypt provides a deployment-compatible memory-hard salted verifier without a native binary dependency. Firestore stores only a bounded attempt counter/lease, hashed challenge tokens, action hashes, expiry, consumption, and audit metadata. Five failures in 15 minutes lock the UID for 15 minutes. A successful verification produces a two-minute HttpOnly action cookie bound to owner UID, exact match, and every proposed input. `AdminVerifiedCoachService` and `AdminVerifiedLineupService` each reload authoritative state and atomically commit challenge consumption, focused writes, and a deterministic success audit. Lineup apply also rejects voting states, ballots, results, and revisions before any new mutation and never writes lifecycle fields. Failure of any write rolls back all of them. Before applying a new mutation, the same transaction checks whether the challenge already names that deterministic success audit. An exact concurrent or ambiguous-response retry then validates the owner, challenge, full action hash, Team, fixture, and immutable audit fields and returns the original receipt without reading or changing mutable Match lifecycle data. This read-only recovery remains valid after voting opens, ballots arrive, or results publish, and after the consumed challenge expires. An expired unconsumed challenge and every mismatched or incomplete receipt fail closed. Raw passphrases, tokens, cookies, provider payloads, voters, and ballots never enter audit records or logs.

Admin authorization forms keep the passphrase out of component state in an uncontrolled password input. Each selected-match step submits one form; the browser performs its zero-write preview and one-use authorization before sending the already bound server confirmation, without exposing action hashes, technical IDs, evidence fields, JSON plans, or exact confirmation strings. Rejected authorization restores the submit control without creating client-side retries. The server accepts plaintext only over the existing HTTPS owner, origin, and CSRF boundary for scrypt verification; responses, cookies, persistence, and logs never echo it. `authenticated-owner` is the explicit stored source marker for these owner attestations, while fixture, owner UID, trusted timestamp, and action hash retain their audit binding.

The dry-run receipt is a short-lived HMAC bound to the owner and exact action, so preview performs zero database writes. `adminActionChallenges`, `adminSecurity`, and `adminAudit` are server-owned deny-all collections; the recursive deny rule also protects verified lineup documents and participants. Audit documents use trusted timestamps and record the owner UID, focused action, match, Team/fixture/evidence, and sanitized outcome. Known pre-commit rejections and transaction failures use separate attempt audits; an indeterminate commit response keeps the short-lived challenge cookie for safe retry and never writes a contradictory failure outcome. The dashboard uses five bounded Team queries rather than one newest-first sample: at most ten preparation candidates for each of `live` and `scheduled`, ten `rating_ready`, ten `rating_closed`, and ten finished `preparing_rating` Matches. Preparation queries share the public four-hour current-Match grace, select only mutable rating states, and order by absolute kickoff ascending before the ten-card presentation limit; live candidates precede scheduled candidates and Match ID breaks equal-kickoff ties. Authoritative rating-state queries remain newest-first so open, expired, invalid, and published sections do not compete with future fixtures. Results are de-duplicated before focused evidence reads. The declared `matches(trackedTeamId,status,ratingState,kickoffAt)` ascending/descending and `matches(trackedTeamId,ratingState,kickoffAt)` descending indexes support these reads; loading `/admin` remains provider-free and read-only. It performs no global Coach query or mutation; coach selection and verification remain in the selected Match workspace. A selected detail reads one match, its focused evidence and participants, the bounded coach roster, and only the global Player documents referenced by that evidence or the owner's draft. It never calls the football provider. Lifecycle failures persist a small diagnostic enum and observation time on the Match; successful readiness clears it.

The visual lineup workspace remains a presentation layer over this same verified-lineup boundary. The selected Match detail preloads its fixture-bound verified snapshot when one exists; otherwise it derives the draft from persisted tracked-Team participants and retains provider participation evidence exactly as stored. The browser never reads Firestore directly. Canonical roster search calls an owner-session-protected, no-store endpoint that issues one bounded indexed membership query, then returns small canonical identity DTOs with available position, shirt, and photo metadata. The browser progressively loads deterministic document-ID pages and de-duplicates canonical IDs across alias boundaries. Historical participant identities remain available after the index repair even when they leave the current roster; an unknown index state fails the request explicitly. Provider aliases continue to be validated by `AdminVerifiedLineupService` during preview and apply.

The selected Match page presents one ordered workflow: starters and participating substitutes, head coach, then final-whistle confirmation and voting close. Completed steps collapse to readable summaries. Provider synchronization controls, raw plans, provider IDs, allocation tokens, and repeated evidence inputs are absent from the primary workflow. Saved drafts, existing verified lineups, canonical internal Players, and verified coach evidence remain the inputs to the same protected services. The server read model derives preparation, active-window, expired-window, published-result, and invalid-window presentation from `ratingState` plus the canonical effective voting window. Active, expired, and published states supersede older `ratingBlockReason` values in owner presentation without deleting that persisted diagnostic evidence. The same read model supplies the manual-opening availability reason, so the checklist, explanation, and action cannot disagree or offer a second opening for an existing window.

Coach verification now materializes both `verifiedCoachAssignments/head-coach` and `coachAssignments/head-coach` in its atomic transaction. Earlier code omitted the second write, allowing the coach panel to report verified evidence while readiness correctly reported no effective assignment. Manual opening supports that legacy partial state by reading the fixture-bound verified evidence and canonical Coach in its transaction. It creates the missing effective assignment together with the final-whistle attestation, audit, and window only when every identity and binding agrees; an existing conflicting assignment, missing canonical Coach, ballots, results, revisions, or invalid lineup aborts all writes.

Before preview, existing Players use the canonical name already loaded with their stable ID. The server applies the shared accent, case, punctuation, and whitespace normalization before detecting a name conflict, then persists the canonical display name. Expected validation failures use stable public codes and safe localized messages. Unexpected preview failures return HTTP 500 with a random correlation ID. Structured logs contain only that ID, operation, safe Match ID, code, and status.

Before this contract, `adminError()` mapped an exact canonical-name rejection and unrelated runtime failures to one generic HTTP 400. The first fixture 1551706 request therefore proved only that it reached this ambiguous fallback. A later categorized `LINEUP_INVALID_INPUT` reproduced after Firestore reads when the optional `Match.trackedTeamExternalProviderId` snapshot field was absent: verified materialization ignored the canonical Team's provider mapping and failed before preview could return. The service now performs one fallback Team document read only for that legacy shape, requires the recovered external ID to identify the fixture's home or away Team, and otherwise fails with a specific safe provider-identity diagnostic. Normal Matches with the snapshot field add no read. Canonical-name normalization, Team ownership, exact fixture binding, 11 starters, explicit participation, owner authorization, and zero-write preview remain enforced.

Drag-and-drop changes only the local draft and maps each drop lane to an existing explicit role/status value. The same moves are available through labeled buttons for touch, keyboard, and assistive technology. Neither interaction invokes a mutation endpoint. A confirmed entering substitute still requires the fixture-wide independent evidence and reason already bound into the preview hash and atomic apply transaction. The server remains authoritative for duplicate identity, Team ownership, alias conflict, starter count, participation, lifecycle state, and protected-history validation.
