# Architecture

## Application shape

Next.js App Router and strict TypeScript form the web application. Pages and layouts are Server Components by default; use Client Components only for browser state or interaction. Tailwind CSS consumes semantic tokens. Domain types and ports do not import Firebase or React.

Public metadata uses native App Router APIs and metadata routes. `src/config/site.ts` is the single canonical origin and public identity source: `NEXT_PUBLIC_SITE_URL` may replace the explicit `https://rating-app-amber.vercel.app` fallback, while arbitrary request and Vercel Preview hosts are never consulted. Root Open Graph/Twitter metadata, the manifest, generated Apple icon, scalable browser icon, and deterministic 1200×630 `/social-card` image require no Firebase, provider, authentication, or request-time data. The social card uses an ordinary route instead of automatic social-image file metadata so `metadataBase`, not the request host, controls its absolute URL. A pure shared builder gives every public page its own relative canonical and complete Open Graph identity because Next.js shallowly replaces nested metadata objects. Static Partidos and Jugadores metadata supplies focused titles and descriptions; dynamic match, result, and player routes construct identity only from encoded route parameters and add no metadata-only reads. Twitter metadata has no route URL field and remains inherited from the root.

The Home-only WhatsApp action uses that same canonical origin to build an encoded `/matches/{matchId}/rate` deep link. Its pure URL helper never reads an incoming or Preview host and adds no voter, ballot, provider, diagnostic, or tracking data.

`src/config` selects the initial club presentation. `src/domain` describes stable business concepts and provider-neutral ports. `src/lib/firebase/browser.ts` lazily initializes one shared web SDK app and derives Firestore and Auth from it only when called and configured. Local mode always connects both services to their explicit emulators and never falls back to a cloud project. Development and production modes require complete Firebase Web configuration. Explicit local scripts use the emulator's REST API; the internal server route lazily initializes Firebase Admin from server-only environment credentials for trusted development/production writes. No Admin object or credential enters browser modules.

Presentation uses semantic game tokens for structure and CSS custom properties for club primary/secondary colors. `AppShell` maps the selected `TeamPresentation.theme` into those properties at the presentation boundary; generic components never depend on Herediano-named colors. Tailwind utilities consume the tokens, while a small set of global conventions supplies crisp panels, status badges, controls, and hard shadows. This changes presentation only and does not localize or duplicate domain data.

## Internationalization

Exactly `es` and `en` are defined in `src/i18n/config.ts`; `es` is the default and fallback. Server Components resolve the `rating-app-locale` cookie on each request. Missing, malformed, and unsupported values resolve to Spanish. The root layout uses the same result for localized metadata and `<html lang>`. A small Client Component renders the language switcher, persists a one-year same-site cookie, and calls `router.refresh()`; it receives its initial locale and labels from the server and does not own a competing locale default.

Routes remain stable and locale-neutral (`/`, `/matches`, and `/matches/{matchId}`, with `/players` deferred) because the current application does not need locale-specific URLs or duplicated route trees. Message resources are bundled TypeScript objects under `src/i18n/messages`; the English resource is statically checked against the Spanish canonical shape, with a runtime alignment test. Translation lookup does not perform network requests. Product-facing dates and numbers use centralized native `Intl` helpers with `es-CR` or `en-US` and Costa Rica display time where appropriate; persisted timestamps remain UTC.

Translations cover presentation labels only. Provider/domain names—including teams, competitions, players, and coaches—remain authoritative proper nouns and are not copied into localized persistence fields. Locale selection and club theme are independent.

## Proposed Firestore model

Top-level collections use generic IDs:

```text
teams/{teamId}
teams/{teamId}/playerMemberships/{playerId}
teams/{teamId}/playerMembershipIndex/state
competitions/{competitionId}
seasons/{seasonId}
players/{playerId}
playerProviderAliases/{aliasId}
playerIdentityReviews/{reviewId}
coaches/{coachId}
matches/{matchId}
matches/{matchId}/participants/{playerId}
matches/{matchId}/coachAssignments/head-coach
matches/{matchId}/verifiedCoachAssignments/head-coach
matches/{matchId}/verifiedLineups/current
matches/{matchId}/lineupDrafts/{ownerUid}
matches/{matchId}/lineupReconciliations/provider
matches/{matchId}/ballots/{voterId}
matches/{matchId}/results/summary
matches/{matchId}/resultRevisions/reopen-{sequence}
players/{playerId}/matchSummaries/{matchId}
players/{playerId}/statistics/{seasonOrCareerId}
standings/{trackedTeamId}
```

The original `ratingReadyAt`, `votingOpensAt`, and `votingClosesAt` fields remain the first-window audit record. An exceptional reopen adds `votingReopenedAt`, monotonic `votingReopenCount`, and the current `effectiveVotingOpensAt`/`effectiveVotingClosesAt`; ordinary matches continue to use the original bounds. `votingClosedEarlyAt` records an operator close. Provider synchronization preserves all of these lifecycle fields.

Each original or reopened window also has one server-owned operator-notification generation. `votingOpenNotificationWindow` uses `0` for the original window and the monotonic reopen count afterward. Status, attempt, lease, first-attempt, sent timestamp, and provider-message fields live on the Match so concurrent lifecycle or operator processes can transactionally claim one send and later retries can observe its durable outcome. Provider synchronization preserves these fields. Ballots, voters, and aggregate data are never notification inputs.

`matches/{matchId}/resultRevisions/reopen-{sequence}` is an operator-owned, server-only immutable snapshot of the former `results/summary`. It retains the complete result, its original `generatedAt`, archive time/reason, revision number, and the window that produced it. Reopen creates this revision, deletes the current summary, and transitions the match to `rating_ready` in one transaction. The deterministic current summary is therefore absent and unpublished while the effective window is active. No query index is needed because revisions use deterministic document reads; existing deny-all client rules already protect them.

The implemented `teams/{teamId}` document contains `displayName`, `shortName`, `countryName`, `countryCode`, `brandingKey`, optional `externalProviderId`, and Firestore `createdAt`/`updatedAt` timestamps. `club-sport-herediano` is the stable initial ID. The seed JSON is the canonical basic Team data; presentation configuration derives its identity and names from that record while keeping theme colors in source code. Firestore snapshots are converted and runtime-validated at the persistence boundary before becoming domain `Team` values.

`standings/{trackedTeamId}` stores one ordered, provider-neutral league snapshot with its internal Competition/Season identity, provider competition/season identity, normalized rows, and provider-sync timestamp. The target is derived from persisted tracked-Team matches joined to a current league Season; it is not hardcoded in the page. A daily trusted sync makes exactly one `GET /standings?league=...&season=...` request and replaces the document atomically only after the entire collection validates. Empty, malformed, or failed responses leave the previous snapshot untouched. `/standings` reads this document only through Firebase Admin, so page views are provider-free and client rules remain deny-all for this collection. No index is required for the direct document read.

An explicit emulator-only script ensures the initial document exists. It requires a local emulator host and a `demo-*` project ID, creates only when absent, and only adds a missing `countryName` to a pre-milestone record. It never runs during application rendering or startup.

A match stores tracked team, its stable provider Team ID, opponent, home/away snapshots, competition, season, kickoff, status, score, provider fixture ID, confirmed goal-event snapshots, optional live elapsed minute, and voting bounds. `Match.id` is always the physical `matches/{matchId}` document ID: persistence writes omit a duplicate payload ID, and snapshot hydration treats the document path as authoritative if a legacy payload contains a stale `id`. Archive, detail, result, ballot, lifecycle, and player-history paths therefore share one durable identity without requiring a data migration. The provider score remains canonical; malformed or incomplete goal incidents are ignored instead of inferred. A durable Player stores provider-mapped identity and current name/position metadata in `players/{playerId}`. A match participant at `matches/{matchId}/participants/{playerId}` explicitly stores internal and provider Team IDs alongside the historical name, number, position, squad role (`starter` or `substitute`), `participated`, and optional confirmed entry/exit minutes. Global Player records never contain match participation or permanent club membership. The tracked Team's head coach has durable identity in `coaches/{coachId}` and one match-specific `matches/{matchId}/coachAssignments/head-coach` document with the same explicit Team ownership; the fixed assignment path models the single rateable coaching role without modeling a full staff. Coach records distinguish `provider` and `operator_verified` identity provenance. Provider identity fields remain optional only for an operator-verified coach and must be a complete real provider pair when present. The server-only `verifiedCoachAssignments/head-coach` audit record binds one verified Coach to the internal Match, tracked Team, provider fixture, HTTPS evidence, reason, operator context, and verification timestamps. Ballot selection requires `participant.teamId == match.trackedTeamId && participant.participated == true`. For the current configuration this selects only confirmed Club Sport Herediano participants and its head coach; opponent players and coaches remain outside MVP rating scope. A future club changes the tracked Team data, not this logic.

`teams/{teamId}/playerMemberships/{playerId}` is a server-owned search read model, not participation or eligibility evidence. Current squad sync, tracked-Team MatchParticipant persistence, and verified lineup apply upsert canonical identity, normalized canonical and historical name prefixes, available presentation metadata, provenance, and first/last observation timestamps. Membership survives transfers, while only explicit tracked-Team evidence can create it; operator-verified provenance is not weakened by a later squad or provider observation. Shared application policy builds and merges this evidence and resolves reviewed aliases for offline and online consumers.

The exhaustive discovery service is restricted to the explicit audit/backfill command. It pages all current-Team Players, tracked-Team Matches and participants, fixture-bound verified lineups, reviewed aliases, and existing memberships; validates bindings; excludes opponents; and creates additive canonical repairs. A successful apply writes `playerMembershipIndex/state` only after every membership batch completes. Online reads require its current schema marker and fail explicitly when it is missing or stale. Admin search performs one 21-document indexed membership query per 20-item page, then bounded Player and alias lookups; its document-ID cursor is deterministic across repeated searches and duplicate aliases. Public history pages the membership index and only final result summaries for the Team, then batch-reads their parent Matches. Its reads scale with indexed Players plus published rated Matches, never with total Matches, participants, drafts, or verified snapshots. The public service rejects a published result identity absent from the complete membership index, preserving public/admin identity parity. The declared `results.teamId` collection-group index supports the public result query.

`matches/{matchId}/lineupDrafts/{ownerUid}` stores the authenticated owner's non-authoritative preparation with Match/Team/provider-fixture binding, participant arrangement, a monotonic version, content hash, and trusted timestamps. Saves permit incomplete lineups, validate every canonical Player against current Team, historical membership, selected-match evidence, or the prior draft, and reject protected voting/result states. Compare-and-set versions reject stale edits; an exact lost-response retry returns the prior receipt. Draft persistence never writes MatchParticipants, VerifiedLineupSnapshot, lifecycle fields, ballots, or results. Verified apply deletes the owner's draft inside its existing atomic challenge/mutation/audit transaction.

`matches/{matchId}/lineupReconciliations/provider` stores one durable fixture-bound provider comparison status and aggregate count. Comparison runs after provider aliases resolve and uses canonical Player identity, starter/substitute role, and participation facts rather than counts or names. Complete compatible evidence records `matched`; a strict subset, unresolved internal-only identity, or unknown participation records `provider_partial`; provider lineup absence records `provider_missing`; extra or different identities, duplicate canonical identities, role disagreement, or contradictory confirmed participation records `conflict`. Persistence is transactional and idempotent: missing or partial retries cannot overwrite an established matched or conflict receipt, a stronger partial can replace missing evidence, and later complete matched or conflicting evidence may replace an earlier conclusive result. The receipt contains no raw provider payload and never weakens verified snapshot precedence.

A completed ballot is one compact document containing `matchId`, `teamId`, `voterId`, a map of player IDs to integer ratings, one `{ coachId, rating }`, and a server timestamp. Its document ID is the verified Firebase UID inside the match's `ballots` subcollection. A trusted Next.js server endpoint verifies the Firebase ID token and derives that UID; the payload cannot select its owner. A Firestore transaction reloads the authoritative match, participants, head coach, and ballot, validates the active server-controlled window and exact eligible ID set, then creates only if absent. Direct client reads and every client write remain denied by rules. This deterministic path plus the transaction enforces `one voter + one match` without a per-score write explosion.

## Aggregation and results

The existing lifecycle trigger finalizes results when trusted server time reaches `votingClosesAt`; no second scheduler or provider call is involved. `AdminFootballSyncStore.finalizeMatchResult` reads the authoritative tracked-Team participants, deterministic head-coach assignment, and private ballots in one Firestore transaction. Every ballot is revalidated with the same exact-key, coach-ID, and integer 1–10 validator used at submission. Any malformed persisted ballot aborts the transaction and leaves the match retryable.

The transaction creates the deterministic `matches/{matchId}/results/summary` document and changes `ratingState` from `rating_ready` to `rating_closed` together. Existing summaries early-exit without changing `generatedAt`; finalized summaries are immutable in the MVP. Raw sums are divided by the valid ballot count and unrounded numeric averages are stored; presentation consistently rounds to one decimal. One ballot is sufficient, zero ballots creates an explicit `no_votes` summary, and every exact top-average player is stored in ordered `mvpPlayerIds`. Coach results remain separate and never enter MVP ranking. Ranked ties use canonical participant order, then stable player ID.

The pilot reads all ballots once at close, which is appropriate for the small community. The aggregate DTO and UI do not depend on the query strategy, leaving a replacement boundary if volume grows.

Jugadores derives player history at read time instead of adding a ratings projection. `AdminPlayerHistoryService` pages the complete Team membership index and final Team result summaries in deterministic batches of 100, then batch-reads only those summaries' parent Matches. Only `rating_closed` matches with an existing `final` summary contribute; `rating_ready`, expired-unfinalized, missing, malformed, and zero-vote results do not. No participant collection, draft, verified lineup, or raw ballot is read. Page or batch failures and index inconsistencies fail the request explicitly instead of returning a catalog described as complete. This is appropriate for the pilot dataset; monitor reads proportional to indexed Players plus published results before replacing it with a trusted idempotent projection.

History groups by canonical `playerId`. A deterministic `playerProviderAliases/{aliasId}` document maps one explicit `(externalProvider, externalProviderPlayerId)` pair to one canonical Player and retains both the observed and canonical provider IDs for audit. Provider IDs are treated as provider-issued references, not permanent real-person identity: future participant and squad syncs resolve or create these aliases before Player persistence. Unknown IDs still produce separate deterministic Players; names, shirt numbers, position, photos, birth data, nationality, or other profile similarity never create aliases automatically.

Operator-created Players use 128-bit random opaque IDs with a `player-internal-` technical prefix. The owner-only allocation endpoint returns a signed owner/Match/Team-bound token and performs no write. Draft persistence validates and retains that token; verified lineup apply validates it again and creates the Player atomically with the authoritative evidence. `playerIdentityReviews/{reviewId}` stores an explicit active or corrected nonmatch decision for one operator-created/provider pair. Same-person review writes the existing deterministic provider alias toward the operator-created canonical survivor, preserves both Player documents and every historical reference, and lets later provider sync enrich trusted fields without replacing operator-verified name or provenance. Queries are bounded by explicit history ceilings and fail closed for duplicate Match identities, conflicting or multi-hop aliases, voting history, ballots, or published provider-ID results. The workflow uses the declared collection-group indexes for `participants.playerId`, `lineupDrafts.ownerId`, and `results.teamId`; it makes no provider request.

Historical participant documents, submitted ballots, and immutable MatchResults keep their original player IDs. Shared discovery maps known legacy IDs to the canonical Player so public history, admin selection, and membership repair agree on identity and Team affiliation. All published matches contribute once to the same profile, average, and ranking, and legacy profile routes resolve to that canonical profile. A canonical Player contributes at most one rating per MatchResult: alias/canonical entries with the same average and vote count collapse to one, while conflicting values reject the malformed result read instead of silently choosing or double-weighting it. Persisted canonical Player metadata wins; a known alias may fill a missing position or photo but cannot replace a usable canonical value with absent data. Missing canonical Player documents are reported by discovery and cannot become selectable identities; immutable result snapshots remain readable historical evidence but do not invent a Player record. Overall average is the arithmetic mean of published per-match averages with full internal precision and presentation-only rounding. Ranking requires two published match ratings and orders by higher overall average, more rated matches, then stable canonical player ID. Player pages are server-rendered through Firebase Admin and perform no football-provider requests.

Current squad presentation metadata is refreshed explicitly with one `GET /players/squads?team=<mapped Team ID>` request. The adapter normalizes API-Football positions to the provider-neutral `PlayerPosition` values and accepts photo URLs only from the narrow API-Sports player-image path. The application resolves each provider ID through the explicit alias layer, then upserts the canonical Player; it never resolves by name or shirt number, deletes nothing, and omits absent optional fields so last-known position/photo metadata survives partial responses. Players absent from the current response and their immutable historical results remain untouched. Repeated identical responses are idempotent. This sync is intentionally separate from match lifecycle polling because roster presentation metadata changes slowly.

Result reads remain behind Firebase Admin. `AdminResultService` checks trusted time before reading the summary, returns a locked state before close, a preparing state after close but before successful finalization, and only returns a sanitized aggregate DTO when both the summary exists and `ratingState` is closed. `AdminMatchArchiveService` reads persisted matches, joins competition labels and deterministic result existence, and supplies the archive/detail routes without provider requests or client Firestore access. Both list and detail scope matches by the internal Team document ID (`club-sport-herediano` for the initial club); provider Team ID `815` remains separate snapshot/provider identity and is never a route authorization key. Shared match-presentation derivation lives in a server-safe module so the Server Component detail route can evaluate it directly, while interactive archive UI remains behind its Client Component boundary. Historical fixtures without voting remain display-only and never enter the active rating lifecycle. Firestore client rules remain deny-all for ballots and results, so neither raw ballots nor voter IDs enter server-rendered HTML.

The result page keeps its public, sanitized aggregate Server Component. A small client section obtains the persisted anonymous voter's ID token and calls a private, no-store comparison endpoint. The endpoint verifies the token, checks trusted close and published result state before reading only `matches/{matchId}/ballots/{verifiedUid}`, and computes the comparison at read time. It resolves player IDs through reviewed provider aliases found from the match participants, requires complete, consistent player and coach matches, and returns no comparison on absent or inconsistent data. No ballot, alias, or voter ID enters server-rendered HTML. No new collection, index, rule, projection, or scheduled task is required.

## Authentication and security

Voting-window recovery uses only the local production CLI. It requires valid production Firebase Admin credentials for an explicitly repeated project ID and a separate high-entropy operator token. The configured `VOTING_WINDOW_OPERATOR_SECRET_SHA256` digest and invocation-only `VOTING_WINDOW_OPERATOR_TOKEN` are compared with constant-time bytes before Firebase access. Missing or mismatched authorization fails closed. No supporter route, browser bundle, Firebase Auth user, or hidden UI exposes these operations.

Verified coach recovery reuses that production Admin and constant-time operator authorization boundary and also requires a configured non-secret `VOTING_WINDOW_OPERATOR_ID` for the durable audit record. Dry-run and apply execute the same transaction reads and validation. Apply accepts only a finished `not_ready` or `preparing_rating` match for the configured tracked Team and exact provider fixture, with no ballot or result. It creates or validates the Coach and deterministic verified assignment together; repeated identical application is a no-op and any identity, evidence, or binding conflict aborts. Direct clients remain denied by the existing recursive Firestore rule.

Reopen dry-run and apply use the same transaction reads and validation. Apply verifies finished/closed state, a current result, auditable timestamps, current participant/coach/ballot consistency through canonical aggregation validation, a bounded requested close time, and a collision-free revision path before any write. Early close reads Firestore's server-assigned document read time, queries ballots inside the finalization transaction, rejects an existing current summary, and invokes the same `aggregateMatchResult` path as scheduled finalization. Firestore transaction retries ensure a concurrent ballot is either committed before the close and included, or observes the closed state and is rejected.

Home and Partidos reuse the same client `BallotEntry` boundary only while a persisted match window is active. It obtains the anonymous voter's ID token and calls the trusted no-store ballot-status endpoint; the endpoint verifies the token, derives the deterministic ballot path, and returns only a sanitized availability/submitted status. Archive and detail DTOs contain no UID, ballot document, or ballot content, and direct client Firestore access remains denied.

Firebase Anonymous Authentication now establishes low-friction voter identity in the browser. The root layout keeps server rendering intact and mounts a zero-UI Client Component that calls the focused auth boundary. That boundary waits for Firebase Auth initialization, reuses `currentUser`, shares concurrent first-load work, and signs in anonymously only when needed. Firebase's native browser persistence retains the UID across normal reloads and visits; the application does not mirror it to local storage or create a `voters/{uid}` document. Local mode connects Auth to `127.0.0.1:9099` once per app, including across Fast Refresh, while development and production never connect to the emulator.

Firebase UID is the canonical `voterId`. Ballot operations cross the trusted server boundary because exact eligibility depends on a dynamic match-participant set that should not be duplicated in browser rules. Authentication is not authorization: current rules grant no match, lifecycle, participant, coach, sync-metadata, or ballot access to an anonymous user. The server endpoint alone verifies identity and authorizes ballot status/submission. Team documents remain public-readable and client-write-denied.

Anonymous identity is device/browser storage identity, not verified person identity. Clearing storage, using incognito, another browser/device, or creating another anonymous account can bypass person-level uniqueness; fingerprinting is intentionally excluded for the initial small supporter group. Future Firebase provider linking can upgrade an anonymous account while preserving its UID where supported. Automatic anonymous-account cleanup is not assumed. App Check is a future public-launch abuse-hardening option, not part of this foundation.

Never expose Admin credentials or raw voter UIDs in normal UI. Public Firebase web configuration is not secret, but belongs in environment-specific files. Use separate development/production projects and Auth/Firestore emulators for local work. Validate App Check and abuse controls before public launch.

## Provider boundary

Goal-event availability remains explicit at the provider boundary. When a provider response omits the event collection or supplies a non-array value, synchronization preserves the existing confirmed goal snapshot. An explicitly returned event array is authoritative after normalization and replaces the snapshot, including with an empty array; malformed individual goal incidents are skipped. Optional live elapsed time follows the same non-destructive omission rule. Scores always come from the provider score fields and are never inferred from goal events.

`FootballDataProvider` is the provider-neutral port. `ApiFootballAdapter` uses native server-side `fetch`, sends `API_FOOTBALL_KEY` only in the provider request header, validates response shapes, normalizes UTC timestamps and statuses, and converts payloads into provider-neutral values. The application sync orchestration depends only on this port and `FootballSyncStore`; UI and voting logic never consume raw provider responses.

The manual sync resolves an unmapped Team by exact normalized name and country, then stores the provider ID only after all fetched data validates. It fetches the Team's competition/season metadata, selects distinct provider seasons overlapping a bounded fixture window (120 days back and 60 days ahead), and queries those seasons sequentially to avoid request bursts. It persists only competition-season pairs represented by fixtures involving the tracked Team. Deterministic IDs derived from provider identities make repeated imports idempotent, while updates preserve document identity and `createdAt`. Match documents store home/away snapshots so opponents do not require a global Team import. The same bounded fixture responses normalize confirmed goal events and optional live elapsed time; archive page views never call the provider. Provider failures abort before writes.

For a specific persisted match, context synchronization has three bounded opportunities. During the final pre-kickoff hour, a scheduled match without a snapshot makes one focused `GET /fixtures/lineups?fixture=...` request after its normal fixture refresh. If the fixture becomes live without a complete snapshot, lifecycle may make at most four fixture-bound lineup retries, at least 15 minutes apart and only when the execution has made exactly its normal fixture refresh. A live attempt therefore uses two provider calls when the fixture lineup contains a usable coach identity, or at most three when the existing narrow Team-coach lookup is needed to recover that fixture coach. Match fields persist the total attempt count, live attempt count, last attempt time, and sanitized outcome before or after the request as appropriate, so separate GitHub Actions executions share the same cooldown and ceiling. `lineupSnapshotAt` records only a successful complete tracked-Team snapshot with exactly 11 starters, at least one substitute, and a fixture-specific head coach; empty, unavailable, partial, malformed, conflicting, and failed attempts keep it absent. An existing fixture-bound operator-verified lineup suppresses automatic pre-match and live capture so provider polling cannot replace its materialized evidence. Before voting can open after `FT`, the independent final reconciliation still makes focused lineup, player-statistics, and event requests even when the live retry ceiling was reached. The provider boundary returns validated participant evidence separately from coach resolution so an ambiguous coach cannot discard otherwise valid players. If the tracked-Team lineup contains a valid coach name but its coach ID is missing or non-numeric, that reconciliation may add one targeted `GET /coachs?team=...` request solely to recover a stable provider ID through an unambiguous exact normalized-name match for the same Team. If the lineup coach object has neither a usable ID nor name, the persisted fixture kickoff is passed to the provider boundary and the same bounded team-coach request may recover identity only when exactly one candidate has a tracked-Team career interval covering that fixture date. A valid current lineup may correct the snapshot only when it is at least as complete; unavailable or smaller observations use the stronger persisted snapshot, and malformed/incomplete evidence performs no context write. A fixture coach published without both player arrays is not persisted independently because the provider-neutral context and its trusted persistence write remain atomic across participants and head coach.

Stable provider Team identity selects the tracked-Team lineup regardless of home/away position or response order. Starters participate by definition only from that trusted lineup. Stable-ID substitution events confirm entering substitutes and entry/exit minutes, while positive player-stat minutes independently confirm entry when populated. A bench player without either signal remains `participated: false`; missing data is never guessed. Events that reference identities outside the trusted tracked-Team lineup fail closed. Only tracked-Team Players and MatchParticipants are persisted. The fixture lineup remains authoritative that a head-coach slot exists for the match; `/coachs?team=...` is only a bounded identity-recovery source. With a valid lineup coach name it must yield exactly one same-Team normalized-name match. With an empty lineup coach identity it must yield exactly one coach whose tracked-Team career interval covers the persisted fixture kickoff date. Persisted latest/current coach state alone never decides an historical fixture. Zero matches, overlaps, wrong-Team careers, malformed identity/career dates, or provider failures remain retryable and unopened. The complete reconciled participant collection atomically replaces older context by stable IDs, preserving `createdAt`; an empty/incomplete provider observation cannot reach that write. Repeated identical evidence is idempotent, and a previously unconfirmed substitute may become participating before voting lifecycle code consumes the records.

An operator-verified assignment is considered only when the provider reports `ambiguous-coach`; missing coach slots, malformed lineups, player-evidence failures, and provider outages still fail closed. The assignment must resolve to its valid internal Coach and match the current Match, tracked Team, provider, and fixture. A later provider coach is accepted only if its real identity agrees with the verified Coach; a different identity is an explicit conflict and writes nothing. Automatic synchronization never overwrites an operator-verified assignment. The final Player, participant, Coach, and head-coach assignment writes occur in one Admin transaction after rechecking lifecycle state, results, ballots, existing verified assignment, and existing head assignment, which prevents partial context under concurrent lifecycle runs.

An operator-verified lineup is fixture-scoped evidence stored at `matches/{matchId}/verifiedLineups/current` and materialized into the existing participant collection. Every entry names a canonical Player and explicitly records starter/substitute role, confirmed-starter/confirmed-substitute/unused/unconfirmed status, independent evidence, reason, owner UID, trusted time, and identity provenance. Internal-only Players are allowed only through an explicit create action and have no provider alias or fabricated provider ID. Alias conflicts, cross-Team Players, duplicate selection, and any lineup other than exactly 11 starters fail closed. Materialization makes only confirmed starters and confirmed substitutes rateable; eleven starters may form the complete snapshot without substitutes.

Final reconciliation passes only persisted provider evidence back to `FootballDataProvider`; it never converts internal verified identities into provider DTOs. If the provider explicitly returns `lineup-unavailable`, final reconciliation may preserve a structurally valid verified snapshot and write its fixture-bound verified head coach through the same atomic participant/coach context transaction. Missing verified coach evidence and every other provider error remain retryable. When provider participants are available, their stable identities and roles are reconciled against the verified snapshot, and a conflict aborts the complete transaction. Empty manual-only reconciliation creates no player alias. Successful repeated reconciliation is idempotent, and lifecycle readiness then applies the standard participant count, coach, and immutable voting timestamp rules.

Provider reconciliation reads that baseline in the same transaction as participant and coach persistence. A missing or smaller provider response cannot erase operator evidence. New provider evidence is compared only after canonical alias resolution. Complete identity sets, lineup roles, and relevant participation facts must agree before the durable status becomes `matched`; missing identities, unresolved internal-only identities, and unknown substitute participation remain partial. An extra or different identity, duplicate canonical identity, role disagreement, or positive participation claim against manually unused/unconfirmed evidence is a conflict and causes the entire context write to fail. Provider data does not silently downgrade or replace verified provenance. This precedence is `operator-verified fixture evidence`, then compatible persisted provider context, then compatible new provider evidence. It does not bypass missing fixture, wrong Team, malformed provider data, or coach validation.

Each lifecycle execution builds an ordered, compact operational trace and emits the same sanitized entries to server logs and the authenticated lifecycle response consumed by GitHub Actions. The trace covers match selection, fixture refresh and normalized status, lifecycle phase, focused lineup/player/event response structure, aggregate participation reconciliation, readiness blockers, voting/finalization decisions, final action, and provider request count. It contains only stable identifiers, states, scores, structural presence, and aggregate counts—never credentials, authorization data, voter or ballot data, player-level payloads, or raw provider responses. Observation is best-effort and cannot change control flow, provider request count, persistence, readiness, or voting timestamps.

Local sync persistence remains restricted to a local Firestore host and `demo-*` project. Trusted hosted lifecycle and ballot operations use Firebase Admin with explicit server credentials. Browser rules continue to allow public Team reads and deny all client access to matches, lifecycle fields, participants, coaches, sync metadata, and ballots; Home and ballot routes read their context on the server.

Live Pro verification on 2026-08-29 used API-Football fixture `1551668` (CS Herediano vs Sporting San José, Primera División, 2026-08-23 UTC). ## Match lifecycle and scheduling

Provider-neutral fixture `status` and the Rating App `ratingState` (`not_ready`, `preparing_rating`, `rating_ready`, or `rating_closed`) are separate Match facts. Focused refresh time, successful participant/readiness time, and voting bounds are compact server-controlled lifecycle fields.

The observed post-match delay has three independent sources: the external trigger may wait up to the approximate 30-minute workflow interval plus GitHub queue delay; the next focused fixture read must first observe provider `FT`; and final lineup/player/event evidence may still be unavailable or conflicting after `FT`. A complete operator-verified fixture baseline removes the provider evidence-publication wait, but it does not remove the need for another lifecycle execution. GitHub scheduled workflows cannot provide a dependable five-minute cadence, so the 30-minute workflow remains the no-cost fallback and the authenticated owner console supplies the bounded prompt trigger for the selected live or recently finished match.

The lifecycle service first reads persisted matches and, before discovery or refresh, selects any expired `rating_ready` match as pending finalization work. That work outranks active windows, live, preparing, scheduled, and historical fixtures until its persisted ballots aggregate successfully; it uses zero football-provider requests, and a failure remains retryable at the same priority on the next trigger. Otherwise active rating windows take priority, then live matches, recently finished/preparing matches, and the earliest relevant scheduled match. Presentation keeps its separate relevant-match selection, so Home and Partidos may feature the next useful fixture while an expired window is safely unavailable pending finalization. A scheduled match remains the relevant candidate for up to four hours after its nominal kickoff so provider status lag cannot make Home or lifecycle jump prematurely to the next fixture; after that grace period, a stale scheduled record no longer blocks the next match. Historical finished fixtures are never backfilled into new voting windows. Fixture discovery is separate from focused lifecycle refresh: when no upcoming match is known it runs at most every 12 hours, while a known fixture uses one `GET /fixtures?id=...` request. Matches beyond 24 hours early-exit; within 24 hours they refresh no more than every six hours, within two hours no more than every 15 minutes, and live/preparing matches refresh whenever the external trigger runs. Postponed/suspended fixtures retry conservatively; cancelled/abandoned fixtures never create a window.

Provider final status alone never opens voting. A finished fixture moves to `preparing_rating`; focused final participant reconciliation must succeed over trusted provider evidence or a compatible operator-verified baseline, at least 11 tracked-Team participants must be rateable, and the deterministic fixture-specific head-coach assignment must exist. Only then does the service set `ratingReadyAt`, `votingOpensAt`, and `votingClosesAt` two hours later. Existing timestamps always win on repeated runs. Manual preparation never writes those fields. Failures leave the match retryable and unopened; terminal rating states do not regress on transient provider status.

The first lifecycle refresh that normalizes the provider fixture to `finished` stores immutable `finishedObservedAt`; this is the trusted observation time, not an inferred final-whistle timestamp. `participantSyncedAt`, `ratingReadyAt`, and `votingOpensAt` provide evidence and opening endpoints, so the owner console can calculate evidence reconciliation and confirmed-FT-to-opening delays without inventing provider publication time. `footballSyncMetadata/{teamId}` records the last execution source, start, completion, outcome, selected match, and provider request count.

Scheduled and owner-triggered calls enter `runConfiguredLifecycle`. A transactional five-minute lease in `footballSyncMetadata/{teamId}` admits one execution and makes overlapping calls return before constructing a provider request. Provider calls have a ten-second bound and renew the matching lease before each read; target selection records the Match on that attempt. Completion clears only the matching attempt, stores its attempt ID and sanitized metrics, and cannot release a replacement lease after stale takeover. The owner flow additionally reloads the exact Match, verifies the canonical lifecycle selection and Team/fixture binding, accepts only live or recently finished unopened states, consumes a one-use passphrase challenge, writes one deterministic authorization audit, and rate limits accepted requests to one per Match per minute.

The same authorization transaction creates `adminLifecycleRequests/{auditId}` with a status separate from Match `ratingState`: `requested`, `running`, `skipped_busy`, `completed`, `failed`, or `voting_open`. The exact consumed challenge remains the credential for status checks and bounded recovery for ten minutes. A request allows at most five claims and three provider executions, with short server-controlled backoff after a busy lease or transient failure. `running` has its own short lease so a lost HTTP response can be recovered. Busy reconciliation records the observed shared lifecycle attempt and only adopts its completion when both attempt and Match agree; otherwise expiry becomes a retryable failure. The owner UI checks status only on explicit operator action. It never writes Match lifecycle state or voting timestamps; the canonical service performs every selection, `FT`, participant, coach, and window check, and `voting_open` requires the persisted active window.

After the window transaction succeeds, trusted server code claims the corresponding operator-notification generation and sends one concise email through Resend. The deterministic provider idempotency key is `voting-open/{matchId}/{windowSequence}`. A short Firestore lease serializes concurrent attempts; unsuccessful delivery returns the generation to `pending`, and later lifecycle runs retry it. Successful delivery records `sent` and suppresses repeats. If a provider response is ambiguous, the same key is reused only inside Resend's documented 24-hour retention period; after 23 hours the generation reports `manual_review` instead of risking a duplicate. Missing configuration and all provider/persistence errors emit sanitized `voting.notification` logs and never prevent, close, or extend the voting window. The same service runs immediately after a successful operator reopen.

A private GitHub Actions workflow runs every 30 minutes and performs only an authenticated `POST` to `/api/internal/match-lifecycle`; it does not check out or install the repository. Missing deployment secrets make scheduled runs exit successfully without calling anything. This uses existing GitHub/Vercel capacity and adds no separately billed scheduler, worker, queue, or always-on service under the current usage assumption; actual plan consumption must still be monitored. `CRON_SECRET` protects the endpoint with constant-time bearer comparison. Vercel holds API-Football and Firebase Admin credentials, while GitHub needs only the endpoint URL and matching cron secret.

A separate private workflow calls `/api/internal/standings-sync` once daily at `09:00 UTC`, equivalent to `03:00 America/Costa_Rica` year-round. It shares the authenticated server boundary but not lifecycle polling, and emits only compact sanitized standings outcomes and counts. GitHub additionally holds `STANDINGS_SYNC_URL`; no provider or Firebase credential is added there.

Controlled live verification on 2026-08-29 discovered API-Football fixture `1551672` (CS Cartaginés vs CS Herediano, 2026-08-30 17:00 UTC) and then refreshed that persisted fixture with exactly one focused provider request. The lifecycle remained `not_ready` with no voting timestamps while the provider status was scheduled, confirming that an away fixture is selected without opening a window early.

Home reads relevant Match data through the server-side Admin boundary, so client Firestore rules remain unchanged. Without Admin configuration or a relevant persisted match, Home retains the honest empty state. With data, a localized scoreboard panel shows upcoming, live, preparing, rating-ready, or finalized context. Selection prioritizes active voting, then live, recently finished/preparing context, the current scheduled fixture including the post-kickoff grace window, then the next scheduled fixture; this prevents provider lag at kickoff from hiding the match in progress while still allowing a truly stale scheduled record to expire. An active rating-ready match links to `/matches/{matchId}/rate`; a finalized match links to `/matches/{matchId}/results`. Both server routes fail closed and expose only their focused sanitized DTOs.

## Multi-team scaling

Every match references a tracked `teamId`; community and theme configuration selects the current context. Collections, indexes, rules, and aggregates remain generic. This supports another club without premature tenant administration or separate schemas.

## Deployment and cost

Deploy the Next.js app to a platform compatible with its server runtime (initially Vercel is suitable) and use Firebase Auth/Firestore free tiers. Prefer static/server rendering, cached provider imports, compact ballot documents, materialized aggregates, and bounded reads. Cloud Functions and scheduled imports are deferred until needed; monitor quotas before opening beyond the initial group.

Hosted runtime configuration is validated centrally before Firebase Admin use. Development and production reject emulator hosts, demo projects, mismatched Web/Admin project IDs, missing credentials, and malformed private keys. Local trusted reads derive Auth/Firestore emulator hosts from explicit local configuration, so unified development cannot silently reach cloud Firebase. Home, ballot, and result routes are force-dynamic with zero revalidation; ballot and lifecycle responses are explicitly `no-store`.

Production begins with one separately guarded, idempotent Team bootstrap that requires production mode, an exact non-demo project confirmation, the stable provider Team ID, and Firebase Admin credentials. Existing emulator seed/sync scripts remain incapable of hosted writes. Once the Team exists, the authenticated lifecycle endpoint uses the normal bounded discovery path to create competition, season, and fixture state. The authenticated read-only `/api/internal/health` endpoint verifies runtime configuration and the canonical Team read without exposing configuration values.

No production environment or deployment is currently configured. `PRODUCTION_RUNBOOK.md` is the operational source for controlled pilot setup, verification, scheduler activation, rollback, and secret rotation.

## Owner console security architecture

The owner console uses the existing Firebase project and email/password provider, with no in-app registration. A named `rating-admin` browser app uses in-memory persistence so signing in never replaces the default app's persistent anonymous supporter. The ID token is checked server-side with revocation enabled, exact `ADMIN_OWNER_UID`, verified email, and password-provider claims before a one-hour Firebase session cookie is issued. Every admin read and mutation rechecks that revocation-aware HttpOnly, Secure, SameSite=Strict cookie. Mutations additionally require an exact configured Origin and a double-submit CSRF token. Login replaces prior admin cookies; logout revokes owner refresh tokens and clears the session, CSRF, and action cookies. Admin pages and APIs are dynamic/no-store, unlinked, and non-indexed.

Sensitive web mutations require `ADMIN_PASSPHRASE_SCRYPT`, independent from Firebase credentials and the CLI operator token. Node's built-in scrypt provides a deployment-compatible memory-hard salted verifier without a native binary dependency. Firestore stores only a bounded attempt counter/lease, hashed challenge tokens, action hashes, expiry, consumption, and audit metadata. Five failures in 15 minutes lock the UID for 15 minutes. A successful verification produces a two-minute HttpOnly action cookie bound to owner UID, exact match, and every proposed input. `AdminVerifiedCoachService` and `AdminVerifiedLineupService` each reload authoritative state and atomically commit challenge consumption, focused writes, and a deterministic success audit. Lineup apply also rejects voting states, ballots, results, and revisions before any new mutation and never writes lifecycle fields. Failure of any write rolls back all of them. Before applying a new mutation, the same transaction checks whether the challenge already names that deterministic success audit. An exact concurrent or ambiguous-response retry then validates the owner, challenge, full action hash, Team, fixture, and immutable audit fields and returns the original receipt without reading or changing mutable Match lifecycle data. This read-only recovery remains valid after voting opens, ballots arrive, or results publish, and after the consumed challenge expires. An expired unconsumed challenge and every mismatched or incomplete receipt fail closed. Raw passphrases, tokens, cookies, provider payloads, voters, and ballots never enter audit records or logs.

Admin authorization forms keep the passphrase out of component state in an uncontrolled password input. Each handler captures its form before asynchronous work, clears the input after authorization succeeds, and then exposes the exact-confirmation step with a visible status. Rejected authorization restores the submit control without creating client-side retries. The server accepts plaintext only over the existing HTTPS owner, origin, and CSRF boundary for scrypt verification; responses, cookies, persistence, and logs never echo it.

The dry-run receipt is a short-lived HMAC bound to the owner and exact action, so preview performs zero database writes. `adminActionChallenges`, `adminSecurity`, and `adminAudit` are server-owned deny-all collections; the recursive deny rule also protects verified lineup documents and participants. Audit documents use trusted timestamps and record the owner UID, focused action, match, Team/fixture/evidence, and sanitized outcome. Known pre-commit rejections and transaction failures use separate attempt audits; an indeterminate commit response keeps the short-lived challenge cookie for safe retry and never writes a contradictory failure outcome. The dashboard reads at most 30 recent Team matches and 100 coaches. A selected detail reads one match, its focused evidence and participants, and only the global Player documents referenced by that evidence or the owner's draft. It never calls the football provider. Lifecycle failures persist a small diagnostic enum and observation time on the Match; successful readiness clears it.

The visual lineup workspace remains a presentation layer over this same verified-lineup boundary. The selected Match detail preloads its fixture-bound verified snapshot when one exists; otherwise it derives the draft from persisted tracked-Team participants and retains provider participation evidence exactly as stored. The browser never reads Firestore directly. Canonical roster search calls an owner-session-protected, no-store endpoint that issues one bounded indexed membership query, then returns small canonical identity DTOs with available position, shirt, and photo metadata. The browser progressively loads deterministic document-ID pages and de-duplicates canonical IDs across alias boundaries. Historical participant identities remain available after the index repair even when they leave the current roster; an unknown index state fails the request explicitly. Provider aliases continue to be validated by `AdminVerifiedLineupService` during preview and apply.

Drag-and-drop changes only the local draft and maps each drop lane to an existing explicit role/status value. The same moves are available through labeled buttons for touch, keyboard, and assistive technology. Neither interaction invokes a mutation endpoint. A confirmed entering substitute still requires the fixture-wide independent evidence and reason already bound into the preview hash and atomic apply transaction. The server remains authoritative for duplicate identity, Team ownership, alias conflict, starter count, participation, lifecycle state, and protected-history validation.
