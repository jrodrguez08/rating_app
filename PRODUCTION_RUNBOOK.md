## Request discipline and autonomous lifecycle

The separate standings workflow runs at `09:00 UTC` (`03:00 America/Costa_Rica`) and calls only the authenticated standings endpoint. It resolves the current league/season from persisted provider-linked football data, makes one bounded `/standings` request, and atomically publishes only a fully validated non-empty table. Empty, malformed, and network-failed responses return a failed workflow outcome while preserving the last valid snapshot. The response/log trace contains stable IDs, row counts, request count, and safe reason codes only. `/standings` reads the persisted snapshot server-side and makes no provider request; Firestore client access remains denied. No additional index is required.

Partidos page reads remain server-only and provider-free. During an active voting window, the existing browser identity boundary makes a separate authenticated, no-store ballot-status request for each rendered actionable match; that endpoint returns only a sanitized status and never exposes a UID or ballot content. A submitted voter is not offered another rating action, status-read failures expose no action, and result visibility remains governed solely by trusted close/finalization.

Provider snapshot merging is non-destructive when a response omits its event collection: already confirmed goal events remain stored. An explicit event array replaces the snapshot after normalization, including when that array confirms no goals. Missing optional live elapsed time likewise preserves the last persisted minute; provider score fields remain canonical.

Before discovery or fixture refresh, every lifecycle trigger checks persisted matches for an expired `rating_ready` window. That pending aggregation outranks later live or scheduled fixtures until finalization succeeds, uses only persisted participants, coach assignment, and ballots, and makes zero API-Football requests. A failed aggregation stays `rating_ready` with its original voting timestamps and is retried first on the next trigger; successful finalization atomically creates the deterministic summary and closes the match without reopening or extending the window.

Every lifecycle trigger evaluates fixture discovery from `footballSyncMetadata/{teamId}.lastFixtureDiscoveryAt`; the check is due when that timestamp is missing, invalid, or at least 12 hours old. A known scheduled, live, or closed Match does not suppress it. A successful provider response, including a valid response with zero fixtures in the existing 120-day-back/60-day-forward window, records the new timestamp and observed count. A provider or persistence failure leaves the previous timestamp unchanged so the next trigger can retry. Structured `lifecycle.discovery` entries report the decision reason, prior timestamp, persisted Match count, discovered fixture count, and provider request count without payloads or credentials. After discovery, a known fixture beyond 24 hours makes no focused provider request; within 24 hours it refreshes at most every six hours, within two hours every 15 minutes, and live/preparing matches on each external trigger. From approximately T-60m through kickoff, a scheduled match adds one focused lineup request only while a complete snapshot is missing; the 30-minute scheduler is approximate, no exact observation time is guaranteed. If the match becomes live without that snapshot, lifecycle permits at most four live lineup attempts, at least 15 minutes apart, and only after the normal fixture refresh with no other provider work in that execution. A live attempt therefore uses two provider calls for a lineup with a usable coach identity, or at most three when the existing narrow Team-coach identity recovery is required. Persisted Match attempt counts, last attempt time, and outcome enforce the cooldown and ceiling across GitHub Actions runs. A complete snapshot or fixture-bound verified operator lineup stops automatic capture. Final readiness remains independent and normally adds three focused requests (lineups, players, events) after the normal fixture refresh, even after the live ceiling. Coach identity recovery can add at most one targeted `/coachs?team=...` request: exact same-Team normalized-name matching when the lineup name is present, or exactly one tracked-Team career interval covering the persisted fixture kickoff date when both lineup ID and name are unusable. Active voting, finalization, and finalized results make no context requests.

Home and Partidos use a separate public selector: active effective voting, a mutable `live` fixture no more than four hours after kickoff, the nearest scheduled fixture, then the newest completed fallback. A `live` Match whose `ratingState` is `rating_closed` is historical presentation, never an active match. This combination can be legitimate after a manually attested final whistle because provider upserts intentionally preserve terminal voting state and the provider status observed at that transition. Diagnose it by comparing the Match's opening mode, voting/result timestamps, `lastProviderSyncAt`, lifecycle trace, and API-Football fixture response; do not edit or normalize the historical document without trusted evidence. Confirm newly discovered fixtures by checking the discovery log count, the persisted Match's provider fixture/Team/kickoff binding, and normal Home/Partidos navigation. An `idle` lifecycle action alone does not prove that discovery ran or that the provider returned a future fixture.
